## Data & interfaces

No schema, endpoint or payload changes. Scope item 1's paragraph states these clauses, in its own words.

- **D1. What a merge's resolution changed is read from the merge commit**, as the paths `git show --remerge-diff --ignore-submodules=none --format= --name-only <merge>` prints: each path where the committed result differs from git's own merge of the two parents. It names a path resolved by hand, and no path for a clean merge or for a file git merged on its own (G6). The flag keeps a moved submodule pointer in the listing, as #1648's flag does for the typed diffs. Where the command does not run, the merge owes what a resolution outside the records owes (G7).
- **D2. A round is owed where D1 names a path outside `agentory/threads/<work-item-id>/`**, before the broad run D3 or D4 owes, and its scope is `agents/proofer.md`'s merge-round paragraph (G15). Where D1 names paths in the records alone, no round is owed, and the inspector reads them (G9). Where D1 names nothing, no round is owed.
- **D3. A merge before the newest broad run owes no broad run beyond the one ahead.** The merge before a branch's next round, or before its broad run, that the *Overlap with the release* ordering asks for stays as G3's paragraph has it.
- **D4. A merge after the newest broad run owes the broad run again, unless the pull request's checks stand in for it.** They stand in where three conditions hold: the pull request is open; its `pull_request` run runs each check the `Broad gate` command runs, which the orchestrator judges as `skills/verify/SKILL.md` *The answerer has to exist* judges an answerer (G13); and `agentic pr-wait <N>` exits 0 at HEAD, where HEAD is the merge commit or a commit after it that changes only the work item's records (G12). The stand-in applies whatever D1 names. A commit of the branch's own after the newest broad run that changes a path outside the records owes the broad run all the same, as the broad gate arm reads it (G4). Under `stop before the pull request`, before the pull request opens, or where the run reads less than the `Broad gate` command, the broad run is taken again.
- **D5. The stand-in counts only while the base's tip is in HEAD, read when the orchestrator hands the pull request over.** GitHub runs a pull request's checks on the head merged into the base as the base stood at that push, and does not run them again when the base moves (G14). So before the orchestrator treats the pull request as checked and ends its run, it fetches the base and runs `git -C <root> merge-base --is-ancestor <base> HEAD`, with `<base>` resolved as `agentic gate` resolves it. Exit 0 means every run at HEAD tested HEAD's own tree, which is the tree a merge into the base as it stands gives (G26). Exit 1 means the base has moved past the run, and the stand-in has lapsed. The orchestrator then merges the base again. That merge owes what D1 to D7 give a merge after the newest broad run, and its push starts the run that stands in, read again the same way. Any other exit code means the base was not read, and the stand-in does not count. The moment the owner presses merge comes after this read and lies outside the tree: only a merge queue or a ruleset could hold it, and that is the owner's (`frame/questions.md` Q2).
- **D6. A merge after the inspector's verdict owes `agentic pr-body` on the body file and the inspector again**, after the round D2 owes and after the broad run or the stand-in D4 takes. Where the stand-in is taken, the orchestrator spawns the inspector after `agentic pr-wait <N>` exits 0. This is G3's paragraph's rule, kept (`frame/plan.md` *Alternatives considered* A3).
- **D7. The orchestrator writes one row of `frame/plan.md` *Judgments of the run* for each merge after the newest broad run, before the inspector's spawn.** The row names the merge commit, the paths D1 printed, what the merge owed, and, where D4's stand-in was taken, the workflow and job whose run stood in, with the grounds of D4's judgment. The inspector reads the row at step 4, and Scope item 6's count reads it after the release.
