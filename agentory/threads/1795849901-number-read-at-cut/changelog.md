### Changed

- **A release takes its number when it is cut, read from the commit subjects it brings to `main` (#1671).** `.github/scripts/release_completeness_check.py` reads `plugin.json` at the base and at the head of the release pull request, and the commit subjects from their merge base to the head. A `feat:` among the subjects makes the number the next minor of the base's version, and its absence makes it the next patch. The check prints the number, the two versions and each `feat:` subject. It fails a head that moves the version to another number, and names the number and each `feat:` subject. A head that moves the major, to a version whose minor and patch are 0, is the owner's word: it passes, and the check prints that it was not read against the subjects. A head that leaves the version where the base has it is the version step's to judge. A subject whose first word is `feat` spelt otherwise is still printed as not read.
- **Work collects on one release branch, `release/next`, which carries no number.** The label workflow puts `merged: next` on each issue that a pull request squashed into `release/next` claims, and labels a push to no other branch. The close-issues workflow takes `merged: next` off each issue it closes, as it takes `size: now` off, and a failed removal is reported while the run goes on. The release check fails where an issue carries `merged: next` and the release does not carry it, and reports an issue the release carries that has no label.
- **The release note reads its pull requests from the tag's range, and its theme from the release pull request's body.** `.github/scripts/publish_release_note.py` lists each pull request whose `(#N)` ends a subject of the range the fragments are read from, with one `gh pr view` for each, and the mark job reads the same set. The release pull request is the one merged into `main` whose merge commit the tag names, found with no head branch name. The theme line is the first sentence of its body. For a note of fragments, a body that cannot be read leaves the note without a theme line, and the job goes on. A note of settles alone carries no theme line, since that body stands whole beneath it, and the job still fails where that body cannot be read.
- **A contribution is based on `release/next`.** `CONTRIBUTING.md` *Opening a pull request*, the pull request template, both READMEs and the version step's refusal name it. `skills/commit-pr-convention/SKILL.md` *Branch names* says that a release branch takes the repository's own name: an integration branch with no number, such as `release/next`, or `release/vX.Y.Z` where the repository names the version when it cuts the branch.
- **The orchestrator routes a gate fix into `main` only where the repository's convention lets a pull request other than the release reach `main`.** `skills/implement/orchestration.md` *Orchestrator: how the work is routed* took `main` when a change's accumulated entries read as one release, or when the change is a gate or a hook firing where it should not. It now takes `main` in those two cases only where the repository's convention lets a pull request other than the release reach `main`. Elsewhere such a change goes to the release branch, which is the default.

### Removed

- **The release automation reads no milestone and no numbered branch name.** The release check no longer reads the milestone `release: X.Y.Z` or the head branch's name, so it no longer fails while a milestone claims an issue the release does not carry, and its `HEAD_BRANCH` input is gone. The refusal of a patch that carries a `feat:` goes, and so does the milestone rename it named as the repair. The release note no longer takes its theme from a milestone's description. The label script no longer maps a branch named `release/vX.Y.Z` to a version, a milestone title and a `merged: X.Y.Z` label.
- **The rules `docs/releasing/` states change through this work item's `## Rule changes`, which the settle after the release writes.** Among them, the version moves in the last pull request into `release/next` before the release pull request opens, a planned milestone is named by its goal and not by a number, and the hotfix route into `main` goes: nothing reaches `main` but the release pull request from `release/next`.
