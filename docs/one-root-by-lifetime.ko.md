# 루트 하나, 수명 순으로 배치한다

*[English](./one-root-by-lifetime.md) · 한국어*

이 플러그인이 저장소에 두는 것은 모두 플러그인이 관리하는 루트 하나,
`seal/` 아래에 있고, 그 안은 각 파일이 얼마나 오래 사는가로 나뉩니다. 이
문서는 그 루트가 어디 있는지, 무엇이 저장소를 옵트인시키는지, 처음 설정이
무엇을 묻는지, 저장소의 설정 행이 무엇을 정하는지를 적습니다.

## 루트와 그 안의 수명

**플러그인이 관리하는 루트 하나가 플러그인이 두는 모든 것을 담고, 각 파일이
얼마나 오래 사는가로 나눕니다.** "관리한다" 는 것은 플러그인이 그것을
만들고 옮기고 지우며, 그 형식을 플러그인의 검사기가 정한다는 뜻입니다.
`.github/` 가 GitHub 의 것인 것과 같습니다. 수명은 셋이고 각각 집이 하나입니다.
세션의 상태는 루트 옆, 공통 git 디렉터리 아래에 있고 커밋되지 않습니다. 작업
항목의 디렉터리 `seal/specs/<id>/` 는 `settle` 이 그 spec 을 적용하고 지울
때까지 삽니다. 그 밖의 `seal/` 아래 파일은 `docs/`, `CHANGELOG.md` 와 함께
영구적입니다. 파일 하나하나의 배치는 `skills/implement/SKILL.md` *Document
layout — two roots, three lifetimes* 와 `docs/the-record-layout.md` 에
있습니다.

**플러그인은 자기 루트에만 씁니다.** 그 밖의 자리에 있는 `specs/` 디렉터리는
프로젝트 자신의 것이고, 이력으로 읽을 뿐 가져가지 않습니다
(`templates/config.md` *Reference specs*). 세션이 칠 수 있는 경로로 루트가
어디 있는지는 에이전트 계약의 `seal/` 루트 절 한 곳에 적혀 있습니다.
check: tests/test_no_document_names_the_old_roots.py tests/test_optin_home.py

## 종속 규칙

**릴리스보다 오래 살아야 하는 것은 병합 뒤에 `seal/specs/<id>/` 를 읽어서는
안 됩니다.** `settle` 이 이 디렉터리를 지우므로, 영구적인 용도에서는 이미
없는 것으로 취급합니다. 라운드 기록의 `target:` 줄은 그 PR 이 열려 있는
동안만 읽힙니다. 릴리스된 changelog 항목 위에서 작업 항목의 이름을 적은
주석은 읽기가 아니라 가리키기이고, 폴더가 없어져도 git 이력에서 찾을 수
있습니다. 저장소에서 이 묶음을 읽는 검사는 모두, settle 이 그 일부를 지울 때
답을 내야 합니다(`skills/settle/SKILL.md` *Answer every check that reads the
corpus*). 병합 뒤에 `seal/specs/<id>/` 를 새로 읽는 코드는 그것을 만난 리뷰가
지적할 일입니다.

**그 뒤에 있는 더 넓은 규칙은, 무엇이 움직일 때 다른 것을 찾아서 고쳐야 하는
관계를 만들지 않는다는 것입니다.** `path:line` 을 가리키는 기록이 이것을
어깁니다. 줄 번호는 그 주장과 무관한 편집에도 움직여서 인용을 다시 잡아야
하고, squash 가 그 인용을 고아로 만듭니다. `settle` 은 불릴 때마다 `docs/` 를
다시 쓰고 디렉터리를 지우므로, 작업 항목 안의 경로나 위치에 묶인 것은
무엇이든 같은 식으로 깨집니다. 남은 묶임은 라운드 기록의 `target:` 줄 하나이고,
그 PR 이 열려 있는 동안 읽히고 기록과 함께 사라집니다.

## 옵트인 신호는 루트 자체다

**저장소가 옵트인한 것은 그 모드의 자리에 `seal/` 이 있을 때입니다.** shared
모드면 `<repo>/seal/`, local 모드면 `$(git rev-parse --git-common-dir)/seal/`
입니다. 훅은 두 자리를 그 순서로 보고, 있는 쪽이 "켜졌다" 와 "어느 모드인가"
를 함께 말해 줍니다. 그 밖에는 아무것도 읽지 않고, 설정 키도 없습니다. git
설정 키도, `.git/` 아래의 표시 파일도, 가져온 ref 도 폴더가 이미 하는 말을
두 번 하는 셈입니다.

| | shared 모드 | local 모드 |
|---|---|---|
| 누가 정하는가 | `seal/` 을 커밋한 사람이, 플러그인을 깐 모든 클론에 대해 | 그 클론의 개발자 |
| 아무것도 설정하지 않은 협업자 | 플러그인을 깔면 게이트에 걸린다 | 그 클론의 git 디렉터리 아래에 루트가 없으니 아무것도 돌지 않는다 |

플러그인을 깔지 않은 협업자에게는 어느 모드에서도 아무것도 돌지 않습니다.
훅이 플러그인의 것이기 때문입니다. 실패 방향은, 두 자리 어디에도 폴더가
없으면 옵트인하지 않은 것이고, 판단하지 못하는 훅은 아무것도 하지 않는
것입니다. 버릴 저장소는 공통 git 디렉터리 아래의 빈 파일
`.git/specseal-scratch` 하나로 게이트를 끕니다. 어떤 커밋도 이 파일을 다른
클론으로 옮기지 못합니다.
check: tests/test_optin_home.py

## 처음 설정에서 무엇을 묻는가

**루트에 대해 질문이 허용되는 때는 처음 설정 한 번뿐이고, 묻는 것도 하나입니다.**
`AskUserQuestion` 한 번에 선택지 둘이고, shared 를 기본값으로 먼저 두며, 각
선택지가 무엇을 하는지 말합니다.

- **shared** 는 `<repo>/seal/` 을 만들고, 라우팅 커밋이 그것을 싣습니다.
  `.github/workflows/hygiene.yml` 이 없으면 `templates/hygiene.yml` 에서
  설치합니다. 설정할 때 깔린 릴리스의 플러그인 클론과, PR 검사 둘입니다.
- **local** 은 `$(git rev-parse --git-common-dir)/seal/` 을 만들고, 트리에는
  아무것도 건드리지 않으며, 아무것도 설치하지 않습니다. 검사는 커밋된 파일을
  읽는데 local 모드는 아무것도 커밋하지 않기 때문입니다.

두 자리 중 어디든 `seal/` 이 있는 저장소는 이미 이 과정을 거쳤으므로 다시
묻지 않습니다. 모드는 폴더가 있는 자리로 읽습니다. 루트가 생기기 전의
배치에 머물러 있는 저장소에는 묻지 않고 알리기만 하며, 세션 시작 훅이 한 번
옮깁니다(`skills/implement/orchestration.md` 의 부트스트랩). 어느 자리에든
루트가 생기면 그 훅은 저장소에 옮겼다는 표시를 남기므로, 나중에 옛 브랜치를
체크아웃한 local 모드 저장소가 깨끗하게 두기로 한 트리 안으로 옮겨지지
않습니다.
check: tests/test_first_setup_asks_once.py

### shared 인가 local 인가

**질문은 "폴더를 커밋하느냐 마느냐" 가 아니라 "CI 와 협업자가 이 워크플로를
보느냐" 입니다.** 어느 답이 맞는지는 대체로 누구의 저장소인가로 정해집니다.

| | local 모드 | shared 모드 |
|---|---|---|
| 맞는 곳 | 이 플러그인의 파일이 트리에 나타나면 안 되는, 자기 규칙이 있는 저장소. 회사 저장소, 남의 프로젝트에 하는 기여. 커밋에 아무것도 더하고 싶지 않은 혼자 쓰는 저장소도 | 자기 저장소, 또는 커밋된 `seal/` 이 아무도 거슬리게 하지 않는 저장소 |
| `seal/` 이 사는 곳 | `.git/seal/`, 공통 git 디렉터리 안 | `<repo>/seal/`, 트리 안 |
| 커밋 | 하지 않는다. gitignore 할 것도 없다 | 한다 |
| 연결된 워크트리와 병렬 세션 | 서로의 기록을 읽는다. git 디렉터리가 클론의 모든 워크트리에 공통이기 때문이다 | 서로의 기록을 읽는다. 파일이 커밋되기 때문이다 |
| 다른 기기와 다시 클론한 경우 | 빈 상태로 시작한다. `seal export` / `seal import` 로 사본을 손으로 옮긴다 | 모두 가지고 있다 |
| CI (체인 검사) | 돌 수 없다. hygiene 워크플로가 설치되지 않는다 | 돈다 |
| 나중에 바꾸기 | `seal mode shared` 가 `.git/seal/` 을 `<repo>/seal/` 로 옮기고 스테이지하고 워크플로를 설치한다. 커밋은 사람이 한다 | `seal mode local` 이 `<repo>/seal/` 을 되돌리고 삭제를 스테이지하고 워크플로를 뺀다. 커밋은 사람이 한다 |

**`seal/config.md` 의 `Mode` 행은 옵트인이 아니고, 차이는 무엇이 그것을
읽느냐에 있습니다.** 그 행은 루트가 *있어야 할* 자리를 말하고, 폴더의 자리는
루트가 *있는* 자리를 말합니다. 어떤 훅, 게이트, 검사도 그 행으로 루트를 찾지
않습니다. 이 질문을 읽는 것은 `hooks/optin.py#home_at` 하나뿐입니다. 손으로
고칠 수 있는 행을 믿는 게이트는 폴더가 없는 자리를 찾아가게 되고, 그 모듈은
짐작하는 쪽이 아니라 *옵트인하지 않음* 쪽으로 실패합니다. 그 행이 주는 것은,
폴더를 옮기기 전에 저장소가 원하는 모드를 말할 수 있다는 것과, 남아 있는
불일치를 검사가 이름 붙여 준다는 것입니다. 행이 없으면 폴더가 있는 자리로
채웁니다. 틀릴 수 없는 값은 그것 하나뿐입니다.

local 모드에 남은 hygiene 워크플로는 영원히 빨간불입니다.
`unverified_check.py` 가 두 번째로 돌면서 어디에도 없는 경로에 대해 2 로
끝나고, `continue-on-error` 가 없으니 잡이 멈춰 `chain_check.py` 는 돌지
않습니다. 돌았다면 아무것도 안 본 채 0 으로 끝났을 것입니다.

**local 모드는 gitignore 한 폴더가 아니라 git 디렉터리 아래에 삽니다.** 연결된
워크트리는 커밋된 파일만 체크아웃하므로, 무시된 `<repo>/seal/` 은 모든
워크트리에서 없는 셈이 되고 병렬 세션이 서로의 기록을 읽지 못합니다. 공통 git
디렉터리 아래에 두면 루트는 그 클론의 모든 워크트리가 함께 쓰고, 커밋 후보가
되지 않으며, `.gitignore` 줄도 필요 없습니다. local 모드에는 커밋하지 않은
상태를 브랜치마다 나누는 장치가 없고, 병렬 항목은 작업 항목별 배치가
갈라 놓습니다. 그 클론, 그 기기를 떠나지도 않습니다. 새 기기나 다시 클론한
저장소는 작업 항목 기록 없이 시작하고, CI 의 체인 검사는 돌 수 없습니다.
맞바꾸는 것은 그것이 전부입니다.

**local 기록은 손으로 다른 클론에 옮길 수 있고, 사본은 동기화가 아닙니다.**
`seal export` 는 루트만, 그 옆의 세션 상태는 빼고, `seal-<repo>-<date>.zip` 으로
묶으며, 내보낸 때의 원격 URL 과 HEAD SHA 를 적은 목록을 넣습니다.
`seal import <zip>` 은 덮어쓰지 않습니다. 없는 파일은 더하고, 이미 있는데
바이트가 다른 파일은 그 옆에 `<name>.incoming<ext>` 로 놓고 알릴 뿐 묻지
않습니다. 나중 사본이 이기고 어느 행이 갔는지는 사람이 챙기므로, 사본이 두 번
필요해지면 shared 모드로 바꿀 때라는 신호입니다. `seal export --check` 는
마지막 내보내기 뒤에 바뀐 작업 항목의 수를 알려 주고, 어디에도 올리지
않습니다.

**모드는 되돌릴 수 있지만 이력은 되돌릴 수 없습니다.** shared 로 가면 기록이
트리에 들어가고, 그 커밋이 들어가는 순간 저장소 이력에 남습니다. 다시
돌아오면 트리에서는 빠지지만 이력에서는 빠지지 않습니다. local 모드가 막으려는
방향이 바로 되돌릴 수 없는 그 방향이므로, `seal mode shared` 는 실행하기 전에
그렇게 말하고, 커밋하지 않고 스테이지만 해서 돌아올 수 없는 지점을 사람에게
남깁니다.
check: tests/test_first_setup_asks_once.py tests/test_optin_home.py tests/test_the_records_can_be_carried_out_and_in.py

## 이름

**제품 이름은 SpecSeal 이고, 그 안의 어휘는 맨 `seal` 입니다.** 루트 `seal/`,
`seal export` / `seal import` 명령, 기록을 가리키는 "the seal" 입니다.

| 이름 | 한 문장 |
|---|---|
| SpecSeal | spec 을 그것을 구현한 코드에 봉인한다 |
| `seal/` | 루트. PR 이 열려 있는 동안 사람이 읽는 것이 진행 중인 작업 항목이므로, `docs/` 옆에 보이게 둔다 |
| `seal/specs/<id>/` | 작업 항목의 디렉터리. 담고 있는 주된 산출물의 이름을 딴다 |

디렉터리는 처음 여는 사람에게 무엇이 들어 있는지 말해야 하므로, 비유로 이름
붙인 디렉터리는 없습니다. smith 와 warden 은 에이전트 페르소나로만 씁니다.
배포되는 산출물은 모두 영어로 씁니다. 플러그인은 남을 위한 것이고 토큰마다
값을 치르기 때문입니다. 저장소 자신의 기록과 PR 을 어느 언어로 쓰는지는 그
저장소가 정할 일이고, 아래에 적습니다.

## 저장소가 스스로 정하는 것, 그리고 그것을 읽는 방법

`seal/config.md` 는 저장소가 자기에 대해 적는 유일한 파일입니다. 항목마다 한
행이고, 검사기가 읽으며, 손으로 고칠 수 있습니다. 있는 행은
`templates/config.md` 에 적혀 있고, 행이 없을 때의 기본값도 코드를 읽는
사람에게 맡기지 않고 거기에 적혀 있습니다.

**아무도 찾을 수 없는 설정은 아무도 가진 적 없는 설정입니다.** 모든 행은 파일
전체를 보여 주고 변경을 연결해 주는 명령 하나로 닿을 수 있습니다. 처음 설정은
질문을 한 번에 묻고 다시 묻지 않으므로, 그 뒤에 생긴 행은 사람이 열어 볼 이유가
없는 템플릿을 읽어야만 찾을 수 있었을 것이기 때문입니다. 연결하는 층은 자기
로직을 갖지 않습니다. 부작용이 있는 행은 그 일을 하는 스크립트로 보내고, 행일
뿐인 행은 바로 씁니다. 스킬 안의 로직은 스크립트처럼 뮤테이션 테스트를 할 수
없고, 경계를 어디에 긋는지는 그것이 정합니다.
check: tests/test_the_settings_have_a_front_door.py

**이 플러그인이 어느 언어로 쓰는지는 플러그인이 아니라 저장소가 답할 일입니다.**
모두에게 영어를 요구하는 스킬은, 그 결정에 동의하지 않는 사람이 고칠 수 없는
파일 안에서 내려진 결정입니다. 그래서 언어는 설정 행에 두고, 번역한 PR 본문을
담는 거울 파일은 언어 하나의 이름이 아니라 그 파일이 담은 언어의 이름을
붙입니다.

**행이 둘인 것은, 하나로는 가운데 답을 말할 수 없기 때문입니다.** 사람들이
