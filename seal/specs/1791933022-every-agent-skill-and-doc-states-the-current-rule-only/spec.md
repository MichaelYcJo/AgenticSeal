## What a definition is, and what the defect is

An agent definition and the skills its `skills:` list injects are the instruction set the model acts on — a `CLAUDE.md` for one role, written into every spawn's context before its first tool call. Three things in such a file are defects in their own right, before any token is counted:

- **A rule stated twice in different words.** The agent receives two instructions for one act and has to reconcile them; where they differ by a nuance, it follows one and is wrong by the other. Measured below: a warden spawn carries four such pairs inside its own context, a smith spawn four, a framer two.
- **A concept that no longer exists.** A rule about a thing the tree removed is a rule the agent tries to apply to nothing, or applies to the nearest thing it can find. Measured below: the preload set names nothing #944 removed, so this class is empty today; phase 2 empties it of the budget concept too, and the review's stage 1 is what keeps it empty.
- **Narrative under a rule.** What a rule used to say, which round found it, what was measured — the agent reads it as instruction, because nothing marks it as story. Measured below: 805 of the 1,693 lines a warden spawn reads sit in paragraphs that open with no rule.

Removing these is expected to improve what an agent does, and the proof below reads outcome first for that reason. The byte and token figures are the cost axis and the second reason.

## The shape of a compact file

A file an agent reads holds rules, formats and links, and nothing that narrates.

1. **A rule is one paragraph.** It opens with the rule in bold, in one or two sentences; a list item whose text opens bold is a rule paragraph too. It holds at most one sentence of why. It ends with what identifies it: `Enforced by: <test node ids>` where a test holds it, and otherwise one link — a `docs/*.md §*heading*`, an issue, or a work item's record at its release tag. Eight live lines is the bar review holds a paragraph to; one needing more is two rules, or a rule and a story.
2. **A format is a fence or a table**, kept whole: a report skeleton, a command, a row shape. A generator parses these, so they are not shortened.
3. **A link replaces a copy.** A rule another file is the home of is one sentence naming the home. The contract keeps §1–§17 with their numbers; a definition keeps its own application of a section and never its sentences; a skill two agents preload is the home of what both need, and the definitions link.
4. **No line outside a rule paragraph narrates.** What a rule used to say, which round found it, what was measured and when — none of it stays. Its homes already exist: git history, the issue the rule cites, the work item's records. A rule whose only grounds were a story keeps the one why-sentence and the link.

## What holds the result — a fact check, a release table, and the review

**The defect is appending and redundancy, and no ceiling measures it** (#923 item 3). A byte ceiling measures a result: a story the same length as the rule it replaced passes it, and holding it brought a price level, `Budget raised:`/`Budget removed:` lines and a listed-file table to keep in step — a second record beside the tree, the shape the evidence ledger had. A history-line count stored per file is the same kind of record; read off a diff instead, it guesses history from words (`#NNN`, `round N`, a date) and so refuses the issue link the principle allows while passing a story that carries none. So nothing of that kind is kept, and three things hold the result instead:

- **The rule every agent carries: a change rewrites the text it amends in place and never appends** (phase 4 states it as a contract section). An agent that appends is breaking an instruction it read, which is what the review reads for.
- **The reviewer reads each document hunk for an append.** `agents/warden.md` (phase 3) states that a hunk adding text beside the sentence it amends, instead of rewriting that sentence, is a finding. This is the one reader that can tell a story from a rule, which no regex could.
- **The release table.** On the release pull request only, one table prints each agent's preload bytes, the suite's seconds, each CI leg's minutes and each document's bytes beside the same reading at the last release tag. It fails nothing; its reader is whoever prepares the release, and a preload or a document that grew is a question that pull request's body answers or an issue it opens.

**One fact is still checked on every pull request: every `Enforced by:` target resolves.** A rule's proof is the test its `Enforced by:` line names (#923 item 4), so a target renamed or removed leaves a rule with no proof, which is a fact the tree can read. `rules --check` (`.github/scripts/rules.py`, phase 2) walks every rule file — `CLAUDE.md`, `CONTRIBUTING.md`, `agents/*.md`, `docs/*.md`, `skills/*/SKILL.md`, `skills/*/orchestration.md`, `templates/*.md` — reads every shown `Enforced by:` line, inside a rule paragraph or not, and resolves each target through `skills/settle/scripts/fold_check.py#target_problem` (a file, a `path::name` unit defined once) or, for `evals/behaviour/<agent>/<case>/`, through the `case.yaml` it holds. Exit 1 names each failure as `path:line §*heading*: why`. One suite case runs it over the tree, so the fact is read where the suite is: locally by `bin/test`, by the sealer's broad gate, and by CI on its three legs. **How it errs:** it cannot tell a test that exists from one that asserts the rule, and a rule written with no `Enforced by:` line is read by nobody — both by the owner's decision, and the review's stage 1 against §*The shape* is what reads them.

**Gate against report.** `rules --check` is the one gate: deterministic, read off the tree. The release table is a report, printed by CI after the suite on a release pull request and read by a person. The proof below is a report too, run by the orchestrator on its own account and carried by the phase record; CI never runs an agent, and no test in the tree makes a later edit owe a run (`plan.md` alternative J). A restatement is removed by the rewrite and counted once at the close by the same Jaccard pass as above, into the changelog fragment and nowhere a checker reads (Q10, answered: no row).

## The proof — outcome first, then cost, on a small set of real cases

Every grader is mechanical: `regex` over a file or the last message, `file_exists`, `tool_used`. No LLM judge scores anything, and nobody reads a report by hand to pass a phase.

**Cost, per run, read off the trace.** The stream-json `result` event of a `claude -p` session carries `total_cost_usd`, `duration_ms` and `usage`; `noninferiority.py run` records them per run beside the graders (built, 7f4b3046), and `compare` writes both sides' pooled spend, tokens read (input + cache creation + cache read) and wall seconds, and the preload bytes of the side's tree. The baseline's first saved `raw.json` is where the field names are confirmed against a real run (Q12).

**The pass rule**, per agent, pooled over the cases × N = 2 runs a side:

1. recall of truth findings, new ≥ old; a deficit of exactly one truth that at least one new run found is noise and passes, anything larger fails naming the findings;
2. false-finding rate, new ≤ old + 0.05;
3. every shape and reach grader at 100 % on both sides;
4. **cost falls**: the preload bytes of the new side are below the old (deterministic, measured by `compare` from each side's tree, held by no row anywhere), and the new side's pooled tokens read and spend are not more than 1.1 × the old's — a compaction that leaves the agent wandering shows up as spend before it shows up as findings. Wall seconds are written and never judged, because the machine's load is in them;
5. a side whose runs were cut by `--max-cost-usd` or a timeout, or whose trace carries no cost, is no result, and the test refuses the record.

The fix on a failure is to restore the rule the output lost, in the shape; the bar never moves in a rewrite phase. Each phase runs the sets of the agents whose preload it changed; the contract phase runs all four. Each agent's last rewrite is therefore already proved on its finished preload, so the close runs an agent's set again only if a file in its preload changed after that agent's last passing record (owner, 2026-10-15).

**Cost of the proof** (from the suite build's measurements; nothing else has run): the baseline ≈ 16 warden runs at ≈ $2.5 plus 22 cheap runs, ≈ $45 and ≈ 1.5 h at `-j 4`; the warden phase the same 16 runs; the contract phase every agent (38); the implementer's pair 16; the framer and sealer 14; the close none unless a preload changed after its agent's last record — ≈ 120 runs and ≈ $150 over the item (Q6, accepted), from the owner's subscription on the orchestrator's account. CI runs none of it.
