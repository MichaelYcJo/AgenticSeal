## What this phase found

**The frame holds for this phase.** `hooks/sealer-stamp-queue.py` already matched `/seal/specs/<id>/guarantee.md` on the path and handed it to `seal_stamp.queue_for_local_guarantee`, which returned nothing for a shared root, as *Technical context* says.

**The writer is renamed, because its name became false.** `queue_for_local_guarantee` is now `queue_for_written_guarantee`: it reads the guarantee at its write under either root. Which root a path is under is `written_root`'s answer. A `seal/` whose parent is a worktree's top and is that repository's root in force is shared mode. A `seal/` whose parent is the git common dir and is the root in force is local mode. Every caller, comment and test was renamed in the same commit.

**Q6, decided: local mode's rule, plus HEAD's history in shared mode, with the refusal record asked of that history.** In shared mode the writer queues where the file reads one `sealed` with no comment line, its `Target SHA` names a commit, no earlier run reads a `sealed` this clone did not refuse, no values file stands for the work item, HEAD's history carries no `sealed` of the file that this clone did not refuse, and the branch `routing.md` names holds the audited commit. The history is read from `HEAD`, not `HEAD^`, because the write is not yet committed. The history test runs before the branch test. So a write over a `sealed` the history already carries queues nothing and records nothing, and only a fresh `sealed` off its branch records a refusal and says so. The spec's wording, *a guarantee that read `sealed` at an earlier commit of HEAD's history*, holds as written once *earlier* is read as earlier than the write, so no divergence is recorded.

**`sealed_before` skips a recorded refusal only where it is handed the clone and the work item.** The write-time writer hands both. `post-commit`'s `_queue_one` hands neither, and keeps its old reading until phase 6 removes it. The reason was measured: with the skip on that path too, `tests/test_commitgate.py::Test_post_commit::test_refuses_to_draw_again_over_a_refused_row_of_a_drawn_seal` went red. In that case a branch is rebased after its seal, a fresh clone's `pre-commit` refuses the rebased row and records its target, and the history still carries that `sealed`, stamped in the first clone. Skipping it would draw the work item a second time. A comment at the call says so.

**For phase 6.** Between phase 4 and phase 6 the tree holds both refusal writers. In the rebase case above, the write-time writer would skip both the earlier run and the historic `sealed`, because `pre-commit`'s record names their target, and so would draw a second stamp at the new audit's write. Phase 6 removes `pre-commit`, and no tree that ships holds both writers, since phases 5 to 7 land in this pull request. A clone that kept a record from an earlier release's `pre-commit` keeps that one exposure after the upgrade. Phase 6 also removes the clauses this phase wrote for the `post-commit` fallback: *or in shared mode at its commit where no write queued it* in `README.md` and `README.ko.md`, the matching clause of `skills/verify/SKILL.md` *Form*, and the last sentence of the stamp paragraph in `skills/code-review/orchestration.md`.
