### Added

- **A repository whose own `seal/` belongs to something else, such as a Python package, can keep its records shared, under `agentic-seal/` (#1059).** Before this release, first setup that met a `seal/` whose `README.md` does not open with the marker wrote nothing into it and put the root under the git directory, in local mode. Such a team could not share its records or run the pull request checks. `lib/optin.py` now holds a second fixed name, `agentic-seal`, found by the same marker. The shared place is `<repo>/seal/` where that directory carries the marker or where nothing stands at that path, and `<repo>/agentic-seal/` where the project's own `seal/` stands. The root in force is read in this order: a marked `seal/`, a marked `agentic-seal/`, then the local root under the common git directory, which keeps the name `seal`. Where both `seal/` and `agentic-seal/` are the project's own, the root goes under the git directory, as a foreign `seal/` did before. A repository whose `seal/` carries the marker reads it as before.
- **Every command and check reads the records under `agentic-seal/` where the root has that name (#1059).** With no root at either place, `seal mode` prints `<repo>/agentic-seal` as the shared place beside a project's own `seal/`. `seal mode shared` and `seal mode local` move the root between `agentic-seal/` and the common git directory and stage the move, and `seal pr-checks install` writes the workflow where the root is `agentic-seal/`. `seal export` still names the zip's members `seal/…`, and `seal import` writes them under the root in force. The pull request's check, `chain_check.py`, reads routing declarations under `agentic-seal/threads/`, reads a change under the project's own `seal/` as a change to code, and reads a pull request that deletes `agentic-seal/` as declaring nothing. `seal stamp --guarantee`, `seal pr-body`, `seal gate`, `seal rules --check`, `seal unverified`, `seal settle`, `seal pact` and `seal fold` read their records and their config there. A message that names a path a person opens prints the path under its real name, and the no-root message of `seal gate` prints the two places `seal mode` prints. This repository's release scripts read the fragments, the documents and the finding counts the same way.
- **The text keeps calling the root `seal/`, and one sentence defines the name (#1059).** The opening paragraph of `skills/core/SKILL.md` says that `seal/` is the root's name in every text the plugin ships, except where a text says a `seal/` is the project's own or that its `README.md` does not open with the marker, and names `agentic-seal/` once. Contract rule 11 and `skills/implement/SKILL.md` *Document layout — two roots, three lifetimes* point at that paragraph. `skills/implement/bootstrap.md` runs `seal mode` before the first-setup question and creates a shared root at the shared place it prints. It offers only local where a directory of the project's own stands at that place too. `templates/setup/seal-README.md` says the same, and says that the by-hand moves end in the root's own name. `README.md` and `README.ko.md` each state the second name on one line of *Shared or local*. A census in `tests/censuses.py` refuses a string constant that spells either name in any module outside `lib/optin.py`, and three cases in `tests/behaviour/test_no_document_names_the_old_roots.py` hold the second name to the core's sentence and to one line of each README.

Updating: nothing to do for a repository whose root is a marked `seal/`. A repository that first setup put in local mode because its own `seal/` stood there can run `seal mode shared`, which moves the root to `agentic-seal/` and stages it.
