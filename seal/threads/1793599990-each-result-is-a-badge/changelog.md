### Changed

- **Each result in a release note's sealed header is now a badge in the seal's reds, not a line of prose (#1299).** After the release is published, the `seal` job of `.github/workflows/publish-release.yml` replaces the note's header with a table. The table's results cell used to read like v0.28.0's: `SEALED v0.28.0 at 40e6c23e on main`, then `10 pull requests merged`, `the suite at 6328 passed and 12 skipped`, `10 work items over 32 review rounds` and so on, one phrase per line, so no number stood out. Each result is now a badge, a small image with a label on the left and a value on the right, drawn by the Shields badge service from its address alone. There are one or two badges to a line: `SEALED` with the version; the commit and its branch; the pull requests merged; the issues closed; the outside contributors where there are some; the suite and its skips; the review rounds and the work items; how many were capped and the issues deferred. The label sits on the seal's dark wax edge, `#8e0c12`, and the value on its raised relief, `#d42420`, both read from `assets/seals/owl.svg`. Each badge's alt text is its label and value in words, such as `suite: 6328 passed`. A reader whose client draws no image therefore still has every result, as does anyone who opens the note while the badge service or GitHub's image proxy does not answer. The results cell is the same where `Release note seal mark` leaves the seal's image off. `.github/scripts/release_seal.py#results` now hands the stamp's results as label and value pairs, and `.github/scripts/publish_release_note.py#sealed_header` draws them. `publish`'s own header, which the seal finds and replaces, keeps its counts as text, so the rule that a second run of the seal edits nothing is unchanged. The badge service's image host joins the domains this repository's census of real identifiers allows. The first note with badges is v0.28.1's, and published notes are left as they are. The plugin ships no release workflow, so no user's repository is affected. The work item's rule changes are in force from this merge, and the settle after the release writes them into `docs/branch-and-release.md` *Cutting a release*.
