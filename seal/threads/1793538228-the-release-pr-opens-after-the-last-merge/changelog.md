### Changed

- **The release pull request opens once the last pull request into `release/vX.Y.Z` has merged, and no longer with the first work item pull request into that branch (#1258).** `docs/release-checklist.md` *5. The release pull request* had the orchestrator open it with the first work item pull request that found none open, and leave it open. Each later squash merge into the branch then reached it as a push, and each push ran `tests` on a tree its own pull request had already tested. On 0.27.2's release pull request, #1251, `tests` ran six times, and only the last run read the tree that shipped. None of the five earlier runs failed, and one of them was cancelled by the next push. The `hygiene` workflow's milestone step was red on every run before the last, by design, so a reader learned to pass over a red check. The orchestrator now reads the moment from two commands after `git fetch origin`. The first is `gh pr list --base release/vX.Y.Z --state open`, which must list no pull request; only this command sees a settle's pull request, because a settle closes no issue. The second is the release pull request's own milestone check, `.github/scripts/release_completeness_check.py`, run by hand with `REPO` taken from `gh repo view`, which must exit 0. Where it names an issue at that point, step 0's milestone box was left undone. The rule is in force from this merge through the work item's rule change, and the settle after the release writes it into `docs/release-checklist.md`. No workflow, script or test changes.
