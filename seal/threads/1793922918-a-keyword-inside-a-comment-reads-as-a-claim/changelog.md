### Fixed

- **A closing keyword inside an HTML comment in a pull request body no longer reads as a claim, as GitHub does not read it (#1181).** The release closer, the `merged:` labeler, the release completeness check, the release note's list of closed issues, the claims check on every pull request and `seal pr-body` all read a body's closing keywords through `.github/scripts/close_issues_on_release.py`. Each of them read `<!-- Closes #6 -->` as a claim, so a release could close an issue that GitHub left open. Throwaway pull requests into `main`, read through `closingIssuesReferences`, measured what GitHub reads. A comment that closes hides its keyword wherever it stands: at a line start, in the middle of a line, over several lines and under a list item (#1402, #1403). A `<!--` that no `-->` follows hides everything below it where it begins a line (#1403, #1405). The same `<!--` after other text on its line is text, and a keyword on the next line is read (#1404). The closer gains `COMMENT`, which reads those three facts. It also gains `HIDDEN`, one pattern over a fence, a comment and a code span, where whichever opens first wins, so a `<!--` inside a code span opens no comment and a backtick inside a comment opens no span. `keywords_in` and `issue_claims_check.py#prose_only` each mask `HIDDEN` in one pass, in place of two passes over the fence and the span. The claims check no longer lists a number that a comment hides as mentioned. `seal pr-body` no longer refuses a copied line whose closing keyword or `details` tag stands inside a comment that closes on the line. A `<!--` that never closes behind a list marker, a block quote marker or an indent hides to the end of the body, though GitHub may end it where the list item or the quote ends. That is the direction that closes fewer. No exit code, message text or command-line interface changes.
