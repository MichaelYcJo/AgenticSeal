## Data & interfaces

**D1. The section's layout, in order.** One paragraph each, unless the item says otherwise.

1. The opening: the orchestrator measures each work item's run once, when it ends, and posts it to one of two logs. One of the two is deleted at every release, so a reading in the wrong one is lost. It names neither label: `test_the_sections_opening_sentence_names_no_single_destination` reads the text before the first `**`.
2. The two logs by kind, kept from `:170-182`: the rolling `flow-measurement` log holds this version's runs and is discarded by the release that ships it; the durable `flow-baseline` log holds readings that span versions. Each is found by its label, with exactly one open. Where no issue has ever carried `flow-baseline`, a cross-version reading stays in the record that would cite it (`:240-244`).
3. The read and the post, when the run ends, that is when the work item's last segment has handed back (the sealer's, where one runs). The orchestrator first reads the run with `seal cost --work-item <the work item's directory>`, which prints the rows the post will carry, any Contract rule 6 line below them and the log's state, and posts nothing. It writes the `--says` file from that reading, then posts it with `seal cost --work-item <the work item's directory> --post --says <file>`. The read comes first because the posting form shows the terminal only its state line (G18). The `--says` file holds the orchestrator's sentence on what the readings say, read against the work item's records, then the run's table (item 6), then the counts of the frame exchange. The post carries one row per segment that no comment on the open log names, each segment's file named on a `# <file name>` line inside its fence. The release's run of the posting command then posts nothing for this work item (G6, `docs/releasing/release-checklist.md` *The release pull request*), except for a segment that ran after this comment. A reading that spans versions takes `--label flow-baseline` on both the read and the post. The orchestrator posts without asking, never as a question (`:427-431`). One sentence says that `--latest`, `--spawns`, `--segments` and `--json`, and how to read their columns, are stated in `session_cost.py`'s module docstring and on the pages they print.
4. What the posting command's exit codes mean, as G7 gives them, and what the orchestrator does at each. Exit 0 also covers the case most installed repositories meet: no issue has ever carried the label, so the post is a no-op, and nothing is posted, nothing fails and nothing asks (`:227-230`). The read of item 3 still runs there, because it is where the orchestrator sees a Contract rule 6 line. The label with a history and nothing open is named in the run's hand-over, and the orchestrator opens no log: opening one is not a session's act, and `docs/running/measuring-a-run.md` *Where a reading goes* holds the reasoning. More than one open log is named, not guessed past. An exit 1 from an empty `--says` reading is the orchestrator's to rewrite, and it runs the command again.
5. The Contract rule 6 line: the read without `--post` prints it where a segment's own transcript holds an `Agent` call, naming that segment's file and its count, and the posted comment carries the same line inside its fence. The orchestrator gives it a home as *Orchestrator: where a decision or a lesson is written* does a lesson about an act.
6. The run's table, `:444-454`, its rows and sources unchanged except that the token row's source says the main transcript is the `*.jsonl` directly under the project directory and is given by path (`:465-471`). Under it, compacted, the paragraphs of `:456-463` (counted, not estimated, with the three `usage` fields), `:473-478` (a comparison against a partial transcript says so in the prose) and `:480-483` (the table carries no verdict).
