## Scope

In:

1. `skills/code-review/orchestration.md` *Orchestrator: the pull request opens once the sealer seals*: the sentence "The wait is `gh pr checks <N> --watch`, …" at lines 226-229 becomes a paragraph of its own, written in place. That paragraph states these facts:
   - The wait is `gh pr checks <N> --watch`. It keeps its stated reason: it reads the checks of every workflow on the pull request, and a single workflow's run can pass while another workflow's check fails.
   - Run before any check has reported on the pull request's head commit, the wait does not wait. It prints `no checks reported on the '<branch>' branch` and exits 1. The fact names gh 2.100.0 as the version it was measured with.
   - Exit 1 is also the exit of a failed check, so the orchestrator does not read that exit, right after a push, as a failure or as nothing to wait for.
   - The wait follows a short poll. The orchestrator runs `gh pr view <N> --json headRefOid,statusCheckRollup --jq '[.headRefOid, (.statusCheckRollup | length)]'` in a fenced block every ten seconds. It stops once the SHA it prints is the commit just pushed and the count is above 0, and then it runs the wait. The SHA keeps the wait off the finished checks of the commit before the push.
   - A poll that has not got there within two minutes is not a pass. The orchestrator reads `gh pr view <N> --json state,mergeable` once more, and the paragraph above says what each reading means. Under `OPEN` and `MERGEABLE`, it says in its report that no check reported on that commit, and names the SHA. It does not wait any longer and does not treat the pull request as checked.
2. `tests/text/test_the_rules_have_one_owner.py#test_the_orchestrator_reads_mergeable_and_integrates_a_conflict_by_a_merge` gains four facts in its `said` tuple: the message `no checks reported on the`, the exit 1 it gives, the read `headRefOid,statusCheckRollup`, and the two-minute limit, each in the spelling the paragraph gives it. Its docstring gains one sentence: #1222 adds the poll before the wait, because the wait run before a check has reported exits 1 without waiting. Each new assertion is seen red against `813665f0`'s `skills/code-review/orchestration.md` before it is committed (contract rule 15).
3. The fragment, `seal/threads/1793521560-the-checks-wait-starts-before-a-check-reports/changelog.md`, holds one `### Fixed` entry and the `### Process changes` row. The entry says that the orchestrator's wait on a pull request's checks, run right after a push, exited 1 with `no checks reported` and did not wait. It also says the wait now follows a poll that ends once the pushed commit has a check, or after two minutes with the report saying that none reported (#1222). The commit that adds the fragment moves `.claude-plugin/plugin.json` from `0.27.1` to `0.27.2`.

## Data & interfaces

No interface of the plugin changes. The guidance reads two of gh's JSON fields on `gh pr view`, `headRefOid` and `statusCheckRollup`. Both were read in this frame's probes with gh 2.100.0. `statusCheckRollup` is the list `gh pr checks` reports from, so a count above 0 is the state in which `--watch` waits.
