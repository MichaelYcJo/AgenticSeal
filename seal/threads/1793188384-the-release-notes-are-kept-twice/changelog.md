### Changed

- **The release notes are kept once, as the GitHub Release at each tag, and built from the changelog fragments (#1053).** A change's note was held three times: in its work item's `changelog.md`, in the gathered `changelog/X.Y.Z.md`, and in the GitHub Release, and two released sentences of 0.12.2 had already drifted from their corrected fragments. On the `vX.Y.Z` tag push, `.github/scripts/publish_release_note.py` now reads every fragment the commits after the previous version tag added, from the history at the tag, so a work item a settle removed before the tag still has its entry. The note opens with the release's theme, the first sentence of the description of the milestone `release: X.Y.Z` with its `Purpose:` label left out. A milestone that cannot be read leaves the note without a theme line, says so in the job log, and never fails the job. The fragments follow the pull request summary, folded, each under its work item's marker, and the link to a file in the tree is gone.
- **`/agentic:update` confirms the version from the installed copy's `plugin.json` and shows what changed from the GitHub Releases (#1053).** Step 2b compares the `version` in the installed copy's `.claude-plugin/plugin.json` with the version the installer reported. Step 3 reads the releases after your old version up to the new one, oldest first, from GitHub's public API with no token, and where that read fails it names the releases page and goes on. **An update from 0.23.1 or earlier reports a mismatch once.** The update runs the skill the old version installed, and that skill reads `CHANGELOG.md` in the new copy at step 2b, finds no file, and stops with *a mismatch*. The update has landed all the same: `.claude-plugin/plugin.json` in the installed copy names the new version, and the notes are on the repository's releases page. The next update runs the new skill.
