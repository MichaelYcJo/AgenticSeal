# Implementation Plan: a release branch requires its checks (#457)

## Technical context

The tree's part is two documents. `docs/releasing/branch-and-release.md` *Work accumulates on a release branch* holds the paragraph **Two rulesets enforce the merge methods.**, its table, the sentence after it, and the new paragraph on the required checks after that. `docs/releasing/release-checklist.md:13-16` holds the first box of *0. Before starting*. The setting is outside the tree. The `release` ruleset is id 23856929 and the `main` ruleset id 23858898 (executed: `gh api repos/MichaelYcJo/SpecSeal/rulesets`). `frame/design.md` *Data & interfaces* holds the `release` ruleset's JSON before the change and the `rules` body after it.

Constraints:

- `tests/text/test_the_release_tail_does_not_end_at_the_tag.py#squash_rule` ends its paragraph at the literal `**Two rulesets enforce the merge methods.**` (design G13). That lead stays word for word.
- The policy text names no released version, such as the release #445 merged into. `tests/behaviour/test_release_hygiene.py` reads loaded documents for version names (read: `:121`, `:247`, `:511`). Policy states the latest rule and not its history (`skills/core/SKILL.md` *The rule a mechanism is kept against*: "History goes to git, the release notes and the work record").
- No `check:` line is added. No case can read a repository setting, and the issue's *Not this* rules one out. Review reads the paragraph.
- The documents wrap as their neighbours do (`tests/behaviour/test_docs_line_wrap.py`).

**Failure scenario of the chosen approach, six months on.** The `test.yml` job named `lint`, or the `hygiene.yml` job named `release`, is renamed. GitHub then waits on a context no job reports. Every pull request into `main` and `release/**` shows the check as expected and cannot merge until somebody edits both rulesets. The failure is loud and blocks everything, which is the safe direction. Its repair is a ruleset edit, which the new paragraph names as outside the tree. The `main` ruleset already carries this risk for the same two names. A second scenario: a workflow is added that pushes to `release/**` directly. The `pull_request` rule already refuses that push today (G6 lists none), so the required checks add no new refusal there.

## Operational impact

**A repository setting changes, outside the tree.** The orchestrator applies Scope 1 once the last round record has no finding open and before it runs `seal gate --preflight`, so the reading of step 3 is committed with the work item's records, the sealer reads S1 and S2 against the live setting, and this pull request is the first to merge under it (design S5). A commit of the reading after the seal would leave `guarantee.md` behind HEAD, and the sealer would run again.

1. Read the `release` ruleset and compare it with the JSON in design *Data & interfaces*. Where it differs, the `rules` body there is stale. Rebuild the body from the live `pull_request` rule before sending it.
2. Send `gh api -X PUT repos/MichaelYcJo/AgenticSeal/rulesets/23856929 --input <file>` with the `rules` body. The repository's current name is `AgenticSeal`: a `GET` under the old name `SpecSeal` follows GitHub's redirect, and a `PUT` under it stops at `HTTP 307` and changes nothing.
3. Run the commands of design S1 and S2, and record their output with the before reading in the work item's records. A row of `## Judgments of the run` below is one such place.

Until step 2 runs, `release/**` takes a red merge as before. After it runs, every pull request into a release branch waits for its `lint` and `release` jobs, and cannot merge while either is red. An empty body does not turn `release` red: `issue_claims_check.py` reads an empty `PR_BODY` as a body and exits 0 (read: `.github/scripts/issue_claims_check.py:293-301`). Cutting the next release branch from `main` is the first act that exercises `do_not_enforce_on_create`. If GitHub refuses that cut, design G7's assumption was wrong and the ruleset is what to correct.

No migration, environment variable or dependency changes.
