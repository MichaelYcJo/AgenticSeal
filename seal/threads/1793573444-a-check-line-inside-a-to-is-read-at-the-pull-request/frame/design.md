## Scope

In:

1. **`rule_changes.Op` carries the lines of each field's value with their line numbers in the design.** The new field `lines` maps each field name to `[(line number, text)]`: the value's lines as they land, each with its line in the design. Leading and trailing empty lines are dropped as `unverified_check.py#field_values` drops them, so the texts joined with `\n` equal the field's value in `Op`. The numbers are taken from `unverified_check.py#items`, whose field holds its first line's number and its lines in order (G7). `old` and `new` keep their meaning, and every caller of `Op` reads them as before. Cases in `tests/skills/test_rule_changes.py` pin a `to` written on its field line, one opened on the line below, and one holding a blank line, each with every line's number.
2. **`.github/scripts/rules.py` reads one text's refusals in one function.** `refused_lines(root, text)` returns `[(line number, heading, why)]` for each refusal of the check lines in one markdown text: `check_lines` composed with `line_problems`. `unresolved` reads each rule file through it and keeps its excuse of a pending `remove`, so what `seal rules --check` prints is unchanged. `tests/github/test_rules.py` keeps its cases and gains one for `refused_lines` on a text holding a held line, a refused line and a near line.
3. **`chain_check.py`'s rule-changes arm reads each check line inside an `add` or `change` `to`.** For each such operation of a design `rule_changes_read` parses, the arm reads the `to` lines (item 1) as one text through `rules.py#refused_lines` and `rules.py#unread_lines`. A refusal is a problem at the design line of the refused value line. Its message names `.github/scripts/rules.py` as the reader `seal rules --check` uses, names the `file` the `to` lands in, and carries the reader's reason. A line `unread_lines` names is a notice at its design line, `not read: <why>`, as the parser's unread lines are. A `from` value, of a `change` or of a `remove`, is read for no check line, since the settle writes neither into the policy root. `chain_check.py` loads `rules.py` by path from the plugin's own `.github/scripts/` once. A `rules.py` that will not load, or that raises its `Unreadable`, ends the check at exit 2 with the reason on stderr, as the rule-changes reader does. The module docstring's *rule changes* arm, and its paragraph on lines the check did not read, say what the arm now reads.
4. **Cases pin the arm at each edge of its scope.** One class in `tests/skills/test_chain_check.py` carries the marker `a-check-line-in-a-to-is-read-at-the-pull-request`, which the rule change below names. It holds these cases. A `to` holding `check: none reader: a, b` is refused at its line on a ready pull request, exit 1, with the reader's reason. A `to` holding `check: none reader: the proofer at review` passes and prints nothing for the design. A `to` naming a path that is no file of the repository is refused at its line. A `to` whose value opens on its field line with a check line is refused at the field line. A `to` holding a near line such as `Check: x` passes, and the line is printed as not read at its design line. The comma line in a `change`'s `from` and in a `remove`'s `from` passes, and nothing is printed for it. A `rules.py` that will not load ends the check at exit 2. Each is seen red before it is planted (rule 15), against the base or under the mutation that reads `from` as well, and the phase record says which.
5. **Every sentence that states what the check reads of a design says it.** `skills/settle/SKILL.md` *A rule has one shape*, the paragraph opening "What this plugin checks, and what it does not", gains one sentence: at the pull request, `chain-check` asks the same reader for each check line inside an `add` or `change` `to`, and refuses a line it refuses at that line of the design. The docstrings of `rules.py` and `rule_changes.py` name the new caller and the new field. The method that lists the class is `git grep -n -e 'rule_changes' -e 'seal rules --check' -e 'rules.py' -- ':!seal/threads' ':!tests'`, run at the build's HEAD and read line by line. A sentence stating what `chain-check` reads of a design is corrected or named in the phase record as still true.
6. **The changelog fragment and the version.** The work item's `changelog.md` fragment, and `.claude-plugin/plugin.json` moved from `0.27.3` to `0.28.0` in the same commit, since this is the first work item into `release/v0.28.0` (`skills/implement/orchestration.md` *Which branch the pull request lands on*).

Out:

- #1216's notice of each test pin and copy a design's operations will break, and #1217's `seal settle --draft`. Both reuse item 1's `Op.lines` and build nothing here.
- A read of the released designs' `to` check lines at the settle's dry run. The pull request reads them first, and `seal rules --check` reads them again once the settle writes them, which catches a target removed after the pull request merged.
- Whether a rule paragraph in a `to` carries a check line at all, and whether its target enforces it. `rules.py` cannot read either, and `skills/settle/SKILL.md` *A rule has one shape* leaves both to review.
- Reading only the `to` values whose `file` matches `rules.py#RULE_FILES`. Every `file` is a top-level document of the policy root, where *A rule has one shape* governs a `to` (`plan.md` *Alternatives considered*, row 6).
- The six lines of the 0.27.1 settle. #1214 reworded each in `docs/`, and no design holds them now.

## Removes

- nothing
  why: the work extends a check's reading and takes no reader, rule or case out of the tree.

This work widens one mechanism: `chain-check`'s rule-changes arm now refuses a pull request it passed before. What it caught before it existed is six check lines the 0.27.1 settle wrote into `docs/` and then reworded by hand (G6, G10). Its cost is one call into `rules.py` per `add` or `change` and one load of that module per run. Nothing goes in return. The only candidate is `seal rules --check` over the rule files, and it stays: it reads the line again once the settle has written it, and it alone sees a target removed between a design's pull request and the settle. The new read adds no reader of the grammar. It calls the one `rules.py` already holds, and `refused_lines` (*Scope* item 2) is that module's own composition, moved so both callers share it.
