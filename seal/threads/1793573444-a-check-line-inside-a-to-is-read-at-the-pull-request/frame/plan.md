# Implementation Plan: a check line inside a `to` is read at the pull request

## Technical context

The work builds on three readers, each read at the branch's base `38095432`.

- `skills/settle/scripts/rule_changes.py#parse` reads a design's `## Rule changes` into `Op(kind, file, section, old, new, line)`. It takes the items from `skills/verify/scripts/unverified_check.py#items`, whose fields are `[first line number, [value lines]]`, and the values from `#field_values`, which joins the lines and strips leading and trailing empty ones. `parse` skips a line only where it lies in a fence, and a fence opened inside a section is refused at the opener or at the line after it (design G7). So in a section that parses, a field's lines are consecutive design lines from its first line, which is what *Scope* item 1 builds `Op.lines` from. The crafter pins that with the blank-line case. Where a case shows a skipped line inside a value, the numbers come from `items` itself, and the phase record says so.
- `.github/scripts/rules.py` reads check lines: `check_lines(text)` and `unread_lines(text)` over one text's shown lines, and `line_problems(root, line)` for the grammar and the targets. `unresolved` composes them over `RULE_FILES` and adds the pending-`remove` excuse. Loading its siblings can raise `Unreadable`, and `markers(root)` raises it for a test file that does not parse. A marker target is the only kind that walks the tree, and on this repository the walk took 0.12 s (executed, in the scratch clone).
- `skills/code-review/scripts/chain_check.py#rule_changes_read` parses each judged or edited design and returns `(path, line, problem)`. `#rule_changes_of` turns a reader that will not load into exit 2. `#load(path, name)` loads a module by path. In a user's repository the plugin is cloned whole beside the checkout (`templates/setup/hygiene.yml`), so `HERE/../../../.github/scripts/rules.py` resolves there as here (design G9).

`chain_check.py` reads the design from git (`read_record`), while `rules.py#target_problem` resolves a target in the working tree under `root`. In CI the checkout is HEAD, and under `--worktree` both read the working tree. A local run without `--worktree` on a dirty tree can resolve a target the commit does not hold; that is how `seal rules --check` already reads, and the CI run is the one that gates.

The failure scenario of the chosen approach, six months on: a `to` names a marker, and a test file somewhere in a user's repository does not parse as Python. `rules.py#markers` raises `Unreadable`, and `chain-check` ends at exit 2, a check that could not run, on a pull request whose design is fine. `seal rules --check` fails the same way on the same tree today, so the two agree. The message names the file that would not parse, which is the fix. A second scenario: #1216 and #1217 grow `Op` further. `lines` is a plain mapping per field, so each reader takes the field it needs and nothing is re-parsed.

## Operational impact

- A user's pull request whose design holds a `to` with a check line the grammar refuses fails `chain-check` once the user's `hygiene.yml` pins a plugin release that holds this work. That is the intended direction: the gate blocks more. A refusal at the pull request costs one reworded line in the same pull request. An allow costs the settling session a hand rewrite with no pull request left, as the 0.27.1 settle paid six times.
- Prompt budget: no question to a person. The refusal reads a fact from the file.
- No new dependency, environment variable, configuration row or migration. The release moves the plugin's version to `0.28.0` (phase 2).
- Platforms: the arm uses `rules.py`'s path handling, which the suite already runs on every leg of `.github/workflows/test.yml`, Windows among them. The new cases run on every leg with no skip.
