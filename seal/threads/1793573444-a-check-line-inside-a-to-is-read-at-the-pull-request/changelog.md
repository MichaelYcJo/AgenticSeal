### Fixed

- **`chain-check` now reads each `check:` line inside a design's rule changes at the pull request, and refuses one that `seal rules --check` would refuse after the settle (#1215).** A design's `## Rule changes` section states, in each `add` or `change`, a `to` value that the settle later writes into the policy documents. The check parsed that section and read none of the `check:` lines inside a `to`. So a line the grammar refuses passed the design's pull request and was first refused by `seal rules --check` once the settle had written it, with no pull request left to fix it in. The 0.27.1 settle reworded six such lines by hand (#1214), each refused for a comma after `reader:`. The check now reads each check line inside an `add` or `change` `to` through `.github/scripts/rules.py`, the reader `seal rules --check` uses. A line that reader refuses, for its grammar or for a target that does not resolve in the tree, is refused at its line in the design with the reader's reason, and a ready pull request fails. A line that opens like a check line and is not one, such as `Check: x`, is printed as not read at its line, a notice in CI, and changes no exit code. A `from` value is not read for check lines, since the settle writes none into the policy documents. Where `rules.py` will not load, or cannot read the tree because a test file does not parse while a `to` names a marker, the check ends at exit 2 with the reason on stderr. A repository's pull requests meet the new refusal once its `hygiene.yml` pins a release that holds it. `seal rules --check` reads and prints as before. Internally, each operation `skills/settle/scripts/rule_changes.py` reads carries its fields' lines with their line numbers in the design, and `rules.py` gains `refused_lines`, which `seal rules --check` and the check share.
