# Phase 1: 1793573444-a-check-line-inside-a-to-is-read-at-the-pull-request

## What this phase found

**The frame holds.** Each claim the build rested on was opened before the first edit. `rule_changes.Op` is built by `parse` alone (`git grep -n 'Op('`), and every caller reads its fields by name, so a seventh field breaks no caller. `rule_changes_of` catches `OSError`, `SyntaxError`, `ImportError` and `SystemExit`, and not `rules.py`'s `Unreadable` (design G4). `field_values` strips the value as `"\n".join(parts).strip("\n").rstrip()` (G7). `chain_check.py` sits three directories below the root, so `HERE/../../../.github/scripts/rules.py` is the module (plan *Technical context*). Run over the eight `frame/design.md` files under `seal/threads/` at this phase's commit, the new arm refuses no line and names none (G8, executed).

**`Op.lines` takes each line's number from the section's body, not from an offset.** `parse` hands `unverified_check.py#items` the body as `[(line number, line)]`, with the lines inside a fence already skipped. A field's parts are consecutive entries of that body from the field's first line, so `value_lines` reads the numbers from the body itself. This holds even where a skipped line stood inside a value, which the plan left open (*Technical context*, first bullet). The trimming follows `field_values` exactly: leading parts that are empty go, trailing parts that are blank go, and the last part's end is trimmed. The texts joined with `\n` equal the field's value in `Op`, and the case asserts that for each shape. Judged against: design *Scope* item 1.

**Two names were added to `chain_check.py` that *Data & interfaces* does not list: a path constant and an exception.** `CHECK_LINES_READER` is the path of `rules.py`. It is a module name so the exit-2 case can point it at a missing file. The class `Unreadable` carries the two ways `rules.py` cannot answer: it will not load, or it loads and raises its own `Unreadable`, as on a test file that does not parse. `rule_changes_of` prints either one on stderr and returns None, so `main` ends at exit 2. Without the class, the second cause would have printed as "the rule-changes reader would not load", which names the wrong reader and the wrong failure. `WRITES_A_TO` names the two kinds read. The one message constant the design names is `CHECK_LINE_SAYS`. Judged against: design *Scope* item 3, "A `rules.py` that will not load, or that raises its `Unreadable`, ends the check at exit 2 with the reason on stderr".

**`rules.py` is loaded the first time a design holds an `add` or a `change`, not when the module loads.** A pull request with no such operation never needs the reader, so a missing `rules.py` cannot fail it. That matches how `unverified_check.py#rule_changes` loads its reader. Judged against: design *Scope* item 3, "loads `rules.py` by path ... once".

**`unresolved` walks each rule file's shown lines twice.** It counts the check lines through `check_lines`, then reads the refusals through `refused_lines`, which walks them again. The excuse of a pending `remove` is now asked once per refusal rather than once per refused line. A line with two refusals asks it twice and gets the same answer. `seal rules --check` printed `all 283 check lines in 55 rule files hold.` at this phase's commit, exit 0 (executed). The output at the base was not run for comparison. Judged against: design *Scope* item 2 and S7.
