## Scope

In scope:

1. **The release note's box states no make-up.** The box **A GitHub Release exists at `vX.Y.Z`** in `docs/releasing/release-checklist.md` keeps three things. First, the commands, `gh release view vX.Y.Z` and `gh run list --workflow publish-release.yml`, and the workflow file they confirm. Second, each state of a missing or partial note and the line or command that says why: no release, the tag step's `no tag:` line, the job's red causes, a title that is the bare tag name, the job log's line saying the pull requests could not be listed, and the `seal` job's `::warning::` line with its causes, a value of the `Release note seal mark` key other than `yes` among them (the key, not a "row"). Third, the repairs: `gh release edit`, and the by-hand seal commands. The box no longer says what a note holds when it succeeds: the header and its counts, the theme line, the pull request folds, `Thanks to`, the badges, where `seal.png` goes, the key's values and the title's source. It cites `docs/releasing/branch-and-release.md` *Cutting a release* for them. That bullet stays the one statement, and it gains nothing.
2. **The workflow's header comment cites the document instead of restating the seal.** In `.github/workflows/publish-release.yml`, the seal paragraph's sentences on what the header holds and on the key's values become one citation of `docs/releasing/branch-and-release.md` *Cutting a release*. The comment keeps how the jobs run: the `created` output, the header guard, `continue-on-error`, and the `dist` job's place and its red. No line outside a comment changes.
3. **The listing's hold is stated once, in `branch-and-release.md`.** After the bold lead **The plugin directory reads `dist`**, which stays word for word, one passage says the listing is on hold since 2026-11-08 by the owner's decision, why (#1420), where the waiting issues are (the milestone `backlog: marketplace listing (on hold)`), and that the `dist` job and the checklist's directory box keep running so that nothing has to be turned back on when it resumes. The paragraph after the lead still names the three kept scripts and their runners. The checklist's directory box keeps its command, what the command reads and prints, that it reports and never fails, the two pages it names (the portal's Submissions page and the Console page), and the `git log -1 --format=%s origin/dist` reading with the re-run. It loses the portal's mechanics, the sentence "The plugin's listing is a portal listing", the #1383 citation and the search inside Claude. It cites `branch-and-release.md` for the hold. After this, no sentence of `docs/releasing/` says that the directory takes, lists or serves a version: "a release the directory did not get" goes too.
4. **The listing case pins the hold.** `tests/text/test_the_release_tail_does_not_end_at_the_tag.py#test_the_directory_box_records_which_kind_of_listing_it_is_with_a_date` is replaced by a case in the same file that reads the hold's sentence in `branch-and-release.md` *Cutting a release* and requires a date, the owner as whose decision it is, and `` `dist` ``. The case is seen red with the date taken out of that sentence (contract rule 15). The paragraph's `check:` line names that file.
5. **The checklist's four headings carry no number.** They become `## Before starting`, `## Settle what earlier releases left behind`, `## The release pull request` and `## After the merge`. `### What a release pull request is held to` keeps its name. Every citation and every "step N" of these headings is rewritten to the new name, in each file `frame/plan.md` *Technical context* lists. A prose mention of a step in a `.py` string literal or docstring is written as a citation, so the census holds it. The text `after_the_tag()` indexes, "Two acts come after the tag", and the box leads the two cases split on stay as they are.
6. **The #1148 sentence states the measure, not the history.** `release-checklist.md` lines 89 to 92 say what the four numbers measure, records that restate one another, and name #1148 once as the grounds, without "which removed …".
7. **No document names #51.** The five references in `docs/releasing/issues-and-milestones.md` name "the open `flow-baseline` issue". Lines 61 to 65 and the `log:` row's Ends cell say that the milestone never closes because a log of each kind is always open in it, and that a ledger can roll to a new issue. `#51` is written nowhere in `docs/`, not even as history.

Out of scope:

- The docstrings of `.github/scripts/publish_release_note.py` and `.github/scripts/release_seal.py`. Each describes its own unit for the person who changes it, which is the home `skills/core/SKILL.md` *The first value: efficient development through the workflow* gives such text. The workflow's comment is in scope because it restates other units' output.
- The lines `plugin_directory_check.py` prints, the `dist` job and every step of the workflow. #1490 *Decided* keeps them. The printed lines describe each kind of listing, and they stay true of a listing whatever its state.
- The `#51` mentions under `tests/`: `tests/github/test_finding_counts.py` line 374, `tests/behaviour/test_release_hygiene.py` line 397, `tests/skills/test_session_cost.py` line 458, and the fixture value `51` in `tests/github/test_roll_flow_measurement_issue.py`. Each is history or a fixture number, none says #51 is open, and #1490 *Done when* names `docs` alone.
- `skills/update/SKILL.md`'s own step `2b.` and the cases that read it. That is another document's step.
- The `*2b*` citation in #1464's body. It is outside the tree. `frame/plan.md` *Operational impact* names it for the orchestrator.
