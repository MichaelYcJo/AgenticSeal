### Fixed

- **The builder's rules now bind an orchestrator that builds a phase or makes a fix itself, as they bind the crafter (#1628, #1629).** Where `routing.md` answers `Implementation` with `the session`, the orchestrator builds every phase and makes every fix pass, and in every route it makes the fix it writes after the last round. The rules for building stood in `agents/crafter.md`, which only a crafter reads, so an orchestrator that built a phase was asked for no mutation run, no case started from its group, no check of the frame before the build and no whole read of its range. `skills/implement/SKILL.md` *Procedure*, which both parties read, now opens with **The builder is the party that builds a phase or makes a fix pass**, and holds those rules said of the builder: **The frame is judged before it is built to** in *1.*, and in *2.* **A new test starts from its group**, **The build holds to the request**, **Find the runner, and type the narrow form**, **Commit before you mutate, and restore from `seal mutate`'s copy**, **Mutation-test every unit that adds behaviour, one command each** and the rule on the read of the range. `agents/crafter.md` opens `skills/implement/SKILL.md` at step 1, and cites the frame rule at step 3, the two mutation rules at step 6, and the rule on the read with the account's rule at step 10. `skills/code-review/orchestration.md` says that the orchestrator builds each phase itself where the session builds, and `skills/implement/orchestration.md` has the orchestrator read the frame against the issue before its own first edit of the build where no crafter is spawned.
- **The orchestrator's records state only facts a command printed or a file showed (#1629).** Step 1 of `skills/implement/orchestration.md` *Orchestrator: the order inside a ticket* gave one reading of which contract rules reach the orchestrator, and `skills/code-review/orchestration.md` gave another. Step 1 now names them: contract rule 21 for its commands, contract rule 19 for the text its commits write, and contract rule 4 and contract rule 5 for every fact that text states of a commit, a run or the tree. Where the orchestrator builds or fixes itself, every rule of the contract binds it as the builder. The other file cites that step.
- **The account of the read before a phase or a fix pass closes now quotes its commands, and `seal range` prints the read (#1624).** Three accounts of #1623's run described a read wider than their commands had printed, because the account was asked for as a description and no command printed what the rule asks to be read: every hunk with the paragraph or unit around it, then the work item's records whole. `seal range <item> --from <commit> --out <file>` writes that into one file. A Markdown hunk prints with its paragraph, bounded by blank lines. Any other text path prints as `git diff -W` prints it, each hunk widened to the same blank-line bound where `-W` stopped short, as it does inside a docstring. A binary path, a deleted path and a path that holds a submodule's commit on either side of the range are named and not printed, so the read goes on past them. The records follow, at HEAD, or on disk where the root is local. The command judges nothing. `skills/implement/SKILL.md` *The account of that read quotes its commands and describes no read in other words* has the account name the commit the read ran at and quote the `seal range` line, its printed lines and the commands of the sample, and says where the crafter and the orchestrator each write it. `skills/implement/fix-pass.md` *The narrow set, then the read of the range* cites both rules and keeps the commit the pass's range starts after and where the orchestrator's account goes.
