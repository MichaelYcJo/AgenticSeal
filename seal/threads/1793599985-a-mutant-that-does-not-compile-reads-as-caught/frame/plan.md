# Implementation Plan: a mutant that does not compile reads as caught (#898)

## Technical context

Every coordinate is at `954bf5a5` in this worktree (read unless labelled).

- **Where a mutant is made and checked.** `skills/verify/scripts/mutation_check.py#mutated` (`:175-194`) refuses an empty OLD, a NEW equal to OLD, and an OLD that does not occur exactly once, each as `Refused`, before any write. `#_held` (`:401-411`) reads the file's bytes once and refuses a file that is not UTF-8. `#mutation_run` (`:307-347`) and `#batch_run` (`:350-398`) call these first, then `_baseline` (`:427-457`), then the write. The compile goes between them. It runs on the original from `_held` and on each mutant from `mutated`, after every pair has landed and before `_baseline`, so a refusal costs no run.
- **How a refusal reaches the reader.** `#main` (`:560-562`) prints `refused: <message>` and returns 2 for any `Refused`. `#batch_run` prefixes a pair's refusal with `pair <n>:` (`:369-373`). A compile refusal raised as `Refused` therefore needs no new branch in `main`, and none in `_report_batch`.
- **Where the exit code is.** `#run_cases` (`:294-299`) writes `(exit N)` into a red's detail. One pair's verdict line prints that detail (`#_line`, `:599-603`). `#_report_batch` (`:621-626`) prints a red or a `SURVIVED` as `mutant <n>: <verdict> (<s>s)` and drops the detail. *Scope* item 4 prints the exit for a red there.
- **Where the not-compiled clause rides.** The first line printed is the verdict for one pair (`main`, `:593`) and the baseline line for a batch (`_report_batch`, `:619`). `skills/verify/SKILL.md:168` says "The first line printed is the verdict, then the command's own output", so the clause joins that first line and no line is printed before it.
- **The tests.** `tests/skills/test_mutation_check.py` is grouped by function (`Test_batch_run` `:89`, `Test_main` `:404`, `Test_module` `:1393`). The cases S1 to S7 join those groups beside `test_refuses_every_pair_when_one_cannot_land_once` (`:125`), `test_a_replacement_that_cannot_land_once_is_refused_before_any_write` (`:683`), `test_a_markdown_file_is_mutated_and_restored_the_same_way` (`:1174`) and `test_accepts_a_batch_whose_every_mutant_is_red` (`:405`, whose line patterns at `:413-414` change for S6). Helpers `world`, `probe`, `red_on` and `seen_runs` already build a target with logged cases.
- **The documents.** The script's docstring has the verdict table (`:32-40`) and the batch paragraph (`:46-63`). `skills/verify/SKILL.md` *`seal mutate` asks condition 2 of one unit, one break at a time* (`:144-225`) has the verdict list (`:170-177`) and the batch line (`:182-190`). `agents/crafter.md:133` sends a reader to the skill for the verdicts, so it does not change.
- **Which `seal` runs.** The installed plugin is 0.28.0 (the orchestrator's executed `which seal`). The worktree's `bin/seal` resolves the tree's script from its own directory (`bin/seal:20-21`). The crafter of this work item runs `bin/seal mutate` from this worktree, so its mutation runs are made by the fixed command once phase 1's code is in. A later item of 0.29.0 does the same from its own worktree (design G11).
- **The version.** `.claude-plugin/plugin.json:4` reads `"version": "0.28.0"`. `docs/branch-and-release.md` *Cutting a release* puts the move to the release's version, now `0.29.0`, in the release's first pull request.

**The failure scenario of the chosen approach, six months on.** The cases' interpreter and `seal`'s drift apart. A crafter on a machine whose `python3` is 3.15 writes a mutant using a construct that 3.15 accepts and the repository's 3.13 virtualenv refuses. The compile passes, the cases fail to import, and the line reads `red`. The exit code on the line may be 1, and nothing else on a batch line shows the cause. That is the false red this work closes, through the gap the design names as its limit (G9). A second scenario runs the other way. A user's repository uses syntax newer than the launcher's interpreter. Its files do not compile as they are, so every mutant runs uncompiled, and the not-compiled clause is the only sign that the refusal is not watching.

## Alternatives considered

| Approach | Failure scenario | Verdict |
|---|---|---|
| A1. Compile each mutant of a `.py` target in process with `compile` over the bytes the write would put on disk, and refuse through the existing `Refused` | The compile uses `seal`'s interpreter, not the cases' (*Technical context*). A mutant that compiles and then fails at import is still read `red`. | Chosen. It is a parser's result, which `skills/core/SKILL.md` *The rule a mechanism is kept against* lets a script gate on. It refuses before any write or run, and it costs about 7 ms per mutant (design G8e). |
| A2. A verdict word of its own, `UNCOMPILED` at exit 2, as the issue proposes | Two exit-2 words would then mean "nothing was written and nothing ran", `refused` and `UNCOMPILED`. Each reader of the verdict list (the skill's list, the docstring's table, a session's `&&` chain) learns a second word for the same outcome. The repair differs only in which text to re-plant, and the refusal's sentence names that. | Rejected. `refused` already covers a mutation that cannot be made as given: an empty OLD, a NEW equal to OLD, a non-UTF-8 file (`mutation_check.py#mutated`, `#_held`). |
| A3. `py_compile` on the file, as the issue proposes | `py_compile` reads the file from disk, so the mutant would be written before it is judged. Without a `cfile` it also writes a `.pyc` beside the source, which is what the command's bytecode step exists to keep away (`skills/verify/SKILL.md` *Why the cache beside the file*). | Rejected for `compile`, which reads the same bytes in memory and writes nothing. |
| A4. `ast.parse`, as `arm_check.py#mutate` does | It accepts a module-level `return`, a top-level `break` and a top-level `nonlocal`, each refused by the compiler (design G8c). Each would still read `red`. | Rejected. `arm_check.py` keeps `ast.parse`, because its operators cannot make those three (design G3). |
| A5. Compile under the cases' interpreter, through a new `--python` option or by spawning the first word of `--tests` | `--tests` is any command and names no interpreter `seal` can read, so the option would be one more argument every caller must pass right. Spawning a second process per mutant would cost a start-up each time to close a limit with no catch on record. | Rejected. The limit is stated in the skill (design *Scope* item 5). |
| A6. Read a red at exit 2, or the words `error during collection` in the output, as no verdict | Exit 2 means a collection error only under pytest, and the tests command is any command. An import error raised inside a test exits 1, the same as an assertion (design G8a). Reading the output would gate on words. | Rejected. Each red line reports its exit code, and the meaning stays with the agent reading the run (design *Scope* item 4). |
| A7. In a batch, mark only the mutant that does not compile and run the rest | A batch already refuses whole, before any run, when one pair does not land exactly once (`#batch_run`, `:369-373`). A second rule for one batch would make "refused" mean the whole call in one case and one pair in the other. A whole refusal costs no run time, because nothing has run yet. | Rejected. |
| A8. Refuse a `.py` target whose file does not compile as it is | Every run on a file that uses syntax newer than `seal`'s interpreter would be refused, though its cases may run under an interpreter that reads it. The user would lose `seal mutate` on that file entirely. | Rejected. The file is named as not compiled, and its mutants are decided by the exit code (`skills/core/SKILL.md`: a script names what it cannot read and decides nothing on it). |
| A9. Replace the literal-text replacement with AST-level operators for `.py` targets, so no non-compiling mutant can be made | The unit a crafter breaks is "a constant, a flipped comparison, a sentence a case pins" (`skills/verify/SKILL.md:146-149`), and the records show runs on `.md` and `.yml` targets (design G10). Operators would lose both. They would also need a vocabulary of operators that grows with every kind of break a crafter wants. | Rejected. The structure kept is the literal replacement on any UTF-8 file. The premise that keeps it was checked: free-form and non-Python breaks are in use (design G10). |
| A10. Keep the command as it is and rely on the agent reading the output under `red` | A batch line prints no output for a red (design G8b). #894's reviewer caught the false red only because it was a single run with an import error printed under it. #1216's sealer met the same kind of red at the end of a run (design G4). | Rejected. |
| A11. Leave a batch's red line without the exit code | A reader of a batch cannot tell a collection error from any other red without re-running each mutant. The single line already carries the code. | Rejected. The code is an exact reading, printed and never decided on. |

## Operational impact

- No new dependency, environment variable or workflow step.
- A run that used to print `red` at exit 0 for a `.py` mutant that does not compile now prints `refused` at exit 2. A `seal mutate ... && seal mutate ...` chain stops there, as it already stops on any run that measured nothing.
- A batch's red line gains its exit code. No script in the tree parses that line (executed: `git grep` for `mutant <n>` and `"mutant ` outside the records found only the script, its docstring, the skill and the test).
- A session that types a bare `seal` runs the installed plugin, and gets the fix only once 0.29.0 is released and installed. Until then, the rounds and the sealer of #883 and #1283 type `<their worktree>/bin/seal mutate`, from a worktree that holds this merge (design G11). The orchestrator writes that path into those spawn prompts.
- No platform-specific code changes. CI's four `windows-latest` legs, on Python 3.12, split `tests/` between them, so `tests/skills/test_mutation_check.py` runs in one of the four (read: `.github/workflows/test.yml:105-108,166`; `questions.md` Q1).
