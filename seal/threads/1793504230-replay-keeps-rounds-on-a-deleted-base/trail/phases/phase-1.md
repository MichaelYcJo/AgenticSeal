**The decisions this phase made, each with its grounds:**

1. **`targets` wraps `written_at` in `functools.cache` and passes the cached function both as WROTE and, for the record's own path, as LANDED.** `round_target` already calls `wrote(rel)` for a record in blocks or in labelled lines, so the landed commit costs no second `git log` there. The cache also answers the next round's path once, where `confirmed` and that round's own read both ask for it. `written_at` stays the one source of the landed commit. Judged against: `frame/design.md` *Data & interfaces*, first bullet ("The crafter may reuse that result instead of calling `written_at` twice, as long as `written_at` stays the one source").
2. **`ref_base` tests the tip by comparing the merge-base with TARGET's full SHA (`resolve(target)`), not with `git merge-base --is-ancestor`.** The two say the same thing: TARGET is an ancestor of the tip exactly when their merge-base is TARGET. The comparison needs no exit code, which this module's `git` helper does not return. A target that does not resolve gives an empty merge-base, so the `base and` guard keeps an empty string from matching an empty `resolve`. Judged against: `frame/design.md` *Data & interfaces*, second bullet ("The crafter picks the test").
3. **Departure: `Test_module::test_a_labelled_target_names_its_base` gained no stubbed `--is-ancestor` answer.** `frame/design.md` Scenario 3's *Verifiable how* cell says it would. Decision 2 asks `resolve` rather than `git merge-base --is-ancestor`. That case stubs `resolve` from a table that does not hold `"T"`, so `resolve("T")` is empty and every base the case expects is kept. The case passes unchanged (executed). Only its comment was rewritten, as scope item 3 asks. Judged against: `frame/design.md` *Data & interfaces*, which leaves the choice of test to the crafter.
4. **Scenarios 2 and 3 are built on a new fixture builder, `deleted_release`, beside `two_layouts`.** `two_layouts` commits each pair of records on top of the commit it reviewed, and names its base as a commit. Scenario 2 needs a writer whose parent is the fork point and which does not hold the target, as a squash makes. One builder with a `squashed` switch gives both scenarios. With the switch off, it commits the records on top of the target. The builder reads the threads layout in `seal` blocks with this tree's check, the shape every record since 0.27.0 takes. Judged against: `frame/plan.md` *Technical context* ("The crafter either widens `two_layouts` with that shape or adds one builder beside it") and the crafter definition's rule that a new test starts from its group: both cases are in `Test_module`, which holds every `targets` case.
5. **Scenario 3's case also checks a ref that resolves and does not hold the target.** The ref is pointed at the fork point, and `ref_base` gives the fork point. Without that check, a `ref_base` that returned an empty string for every resolving ref would pass the case. Judged against: `skills/verify/SKILL.md`, the rule that a check has to be able to fail.
