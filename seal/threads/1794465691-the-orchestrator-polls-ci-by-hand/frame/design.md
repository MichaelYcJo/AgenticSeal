## Data & interfaces

```
seal pr-wait <N>          wait on pull request N's checks at this checkout's HEAD
seal pr-wait <N> --once   read pull request N's state once and wait on nothing
```

**What it compares against.** The SHA is HEAD of the working directory, read with `git rev-parse HEAD` through `lib/gitcmd.py#argv`. The orchestrator pushes HEAD, so HEAD is the commit it pushed last.

**What each poll reads**, every ten seconds, in this order:

1. `gh pr view <N> --json state,mergeable,headRefOid,statusCheckRollup`.
2. Once `state` is `OPEN`, `mergeable` is `MERGEABLE`, `headRefOid` is HEAD and the rollup is not empty: `gh pr checks <N> --json name,workflow,event,bucket`. An empty rollup is read from the first call's exit 0 and never from the second call's exit 1, so a `gh` error is not taken for "no check yet" (G6).
3. Once at least one check has event `pull_request` and none is `pending`: `gh run list --commit <HEAD> --event pull_request --json status,workflowName`. Where every run is `completed`, the command reads `gh pr checks` once more and decides on that read where nothing in it is `pending`; where a check is `pending` again, it polls on.

**The exit codes.** Each outcome G3 distinguishes takes one, and exit 2 is the command's own:

| Exit | When | What the orchestrator does (*Scope* item 4 states it) |
|---|---|---|
| 0 | the decisive read holds only `pass` and `skipping` | treats the pull request as checked at HEAD |
| 1 | the decisive read holds a `fail` or a `cancel`; the output names each such check by workflow and name | reads the named checks' logs and repairs |
| 2 | the command could not ask or could not read the answer: no `gh`, a `gh` call that exits non-zero, a `bucket`, `state` or `mergeable` value that is none of those G7 and G3 name, an unusable argument, or no HEAD | reads the message; nothing about the pull request is known |
| 3 | within two minutes of the start, the head never became HEAD, `mergeable` was never known, or no `pull_request` check was listed on HEAD; the output says which and names the SHA | reports that no check of a `pull_request` run reported on that commit, and does not treat the pull request as checked |
| 4 | `state` is `MERGED` | puts the repair on a new branch cut from the base |
| 5 | `state` is `CLOSED` | pushes nothing, and reports that the pull request was closed with a repair pending |
| 6 | `state` is `OPEN` and `mergeable` is `CONFLICTING` | merges the base into the branch |

Exits 4, 5 and 6 are taken at whichever read first shows them. The two-minute limit runs from the start until the first `pull_request` check is listed on HEAD, and no limit applies after that. Under `--once` the command runs the first read alone and exits 0 for `OPEN`, 4 for `MERGED` and 5 for `CLOSED`.

**What it prints.** An argument `argparse` refuses prints its usage error on stderr at exit 2. Every other exit prints one line on stdout that opens `seal pr-wait:` and names N, the SHA and the outcome. Exit 1 adds a line for each check in `fail` or `cancel`, and exit 2 adds the `gh` or `git` command and its stderr. The crafter writes each line's words, and a case pins each (contract rule 14).
