### Added

- **A pull request body can carry the seal mark once the work item is sealed (#1204).** The seal mark used to be drawn only in the terminal, as the stamp after the sealer's verdict. Now a repository can turn it on for the pull request body with one row in `seal/config.md`, `| Pull request seal mark | yes |`. Where the row reads `yes`, `seal pr-body` writes the plugin's icon as one image line under the `## From the records` heading, above the fold. It writes the line only where the newest verdict block of the work item's `guarantee.md` reads `sealed` at HEAD, or at a commit that only `trail/gate.md` and `guarantee.md` follow. A body rewritten after a later repair carries no mark until the repair is sealed. The image's address is the plugin's repository at the tag of the plugin's version, so it shows while that repository stays public and the tag exists. An absent or empty row puts no mark and says nothing. Any other value, such as `Yes` or `on`, a row written twice, a guarantee whose base the clone cannot resolve, and a plugin manifest the address cannot be built from each put no mark and are named on one line opening `seal pr-body:`. None of them changes the command's exit code. The sealer checks the body before its own verdict exists, so the orchestrator now runs `seal pr-body` once more after it commits a `sealed` guarantee, before it opens the pull request. That run changes no copied line. The terminal stamp is unchanged. The rule is in force from this merge through the work item's rule changes. The settle after the release writes it into `docs/the-review-record.md` *The guarantee*.
- **The release note's seal image is turned on by its own row (#1204).** The release's `seal` job used to attach the seal image and show it beside the results in the note's header on every release. Now it does that only where this repository's `seal/config.md` reads `| Release note seal mark | yes |` at the tag, which it does. Under any other value the job attaches nothing, and the note's header becomes a table of one cell holding the same results, in the same order, as the image's neighbour held. A value other than `yes`, and a row written twice, are named on a `::warning::` line, and the job still ends with an exit of 0. The plugin ships no release workflow, so the row is read in this repository alone, and `templates/setup/config.md` says so. The rule is in force from this merge through the work item's rule changes. The settle after the release writes it into `docs/branch-and-release.md` *Cutting a release* and `docs/release-checklist.md` *6. After the merge*.
