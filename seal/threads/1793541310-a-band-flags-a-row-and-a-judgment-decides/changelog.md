### Changed

- **A reading that moved past its band is weighed against what the change bought, and an issue follows only a reading judged `worse` (#1263).** A band is how far a reading may move from the reading it is compared with and still read as the same. It tells a moved reading from noise, and it cannot say whether what a change cost outweighs what the change bought. On 0.27.2, the measurement of the process read two rows past their band as `worse` and filed an issue for each. One of them, #1259, reported that a session in this repository started with 9,658 B of plugin text where 0.21.1 started with 9,261 B. The 397 B came from the core now reaching every session from one source, and the owner closed #1259 as not planned. Now the party that writes a reading also writes the weighing beside it: the change that moved it, what that change cost, what it bought, and the record each stands in. The reading is `worse` only where the cost outweighs what was bought, and the orchestrator files an issue only for a reading judged so. The release table on the release pull request has no band, so a preload or a document that grew is a row for the same weighing, which the orchestrator writes in the pull request's body. Before this change such a row was a question the body answered or an issue it opened. The rule is in force from this merge through the work item's rule changes. The settle after the release writes it into `docs/measuring-a-run.md` *What a measurement must survive, and what it must not invent*, cites it from `docs/release-checklist.md` *5. The release pull request*, and names it in the index row of `docs/README.md`. No script, workflow or test changes.
