### Changed

- **A reading that moved past its band is weighed against what the change bought, and an issue follows only a reading judged `worse` (#1263).** A band is how far a reading may move from the reading it is compared with and still read as the same. It tells a moved reading from noise, and it cannot say whether what a change cost outweighs what the change bought. On 0.27.2, the measurement of the process read two rows past their band as `worse` and filed an issue for each. One of them, `#1259`, reported that a session in this repository started with 9,658 B of plugin text where 0.21.1 started with 9,261 B. The 397 B came from the core now reaching every session from one source, and the owner closed `#1259` as not planned. Now the party that writes a reading also writes the weighing beside it: the change that moved it, what that change cost, what it bought, and the record each stands in. The reading is `worse` only where the cost outweighs what was bought. The orchestrator writes the weighing in a release pull request's body, the settling session in its comment on the `flow-baseline` issue, and the crafter in the phase record of a work item that measures the process. An issue follows only a reading judged `worse`, and the orchestrator or the settling session files it, with one exception at the settle. There the settling session says of each records-alone finding that kept the count up whether it found a stale copy, a record that restates a fact another record holds and was left as it stood when that source changed, which is what #1148 removed. The count is `worse` only where stale copies are what kept it up, a count that held level is read as one that rose, and #1020, already open, is the issue that follows, so the settling session files no other. The proofer reads the weighing at review, and the owner reads it before a release or settle pull request merges. Two readings with no band turned a number into a verdict directly, and both are now rows for the same weighing. On the release pull request, a preload or a document that grew in the release table was a question the body answered or an issue it opened. At the settle, a records-alone count that did not fall, the number of review findings whose location names only a work item's own records as `.github/scripts/finding_counts.py` counts them, said the records still restated one another and named #1020's check as the next step. A margin a claim fixes before its run is not a band: the behaviour suite's pass rules, which decide whether one preload rewrite proved itself not worse, stay as they are and file nothing. The rule is in force from this merge through the work item's rule changes. The settle after the release writes it into `docs/measuring-a-run.md` *What a measurement must survive, and what it must not invent* with the sentence that places the behaviour suite's margins outside it, cites it from `docs/release-checklist.md` *2b. Settle what earlier releases left behind* and *5. The release pull request*, and names it in the index row of `docs/README.md`. No script, workflow or test changes.
