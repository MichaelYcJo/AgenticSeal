### Added

- **The release pull request refuses a release named as a patch whose own commits carry a `feat:` (#1199).** A `feat:` makes a minor. The step that judges the release's milestone, now named `the milestone this release claims is the work it carries, and a patch carries no feat`, also reads the release branch's commit subjects since it left `main` against the version in the branch's name. Where the version's third number is not 0 and a subject opens with `feat:`, the step fails, names each such subject, and states the repair: rename the release's milestone and every later planned `release:` milestone one step forward, cut the branch again under the new name, and move `plugin.json` in the new branch's first pull request. The reading counts the one spelling `feat:`. A subject whose first word is `feat` spelt otherwise, such as `Feat:` or `feat(agents):`, is printed as not read and fails nothing. Every run prints how many `feat:` subjects it counted and whether the version is a patch or a minor, and a minor with none says it ships as the minor it was named. The reading runs where the release's milestone does not exist as well. Of the 37 patch releases from v0.8.1 to v0.25.1, 14 carried a `feat:` subject, under a rule approved on 2026-09-02 that nothing held (#653).

### Changed

- **A prefix is the writer's judgment of what the change does for whoever meets it, guided by each kind's meaning and examples and stated with its grounds, and a repository's log no longer decides it (#1199).** `skills/commit-pr-convention/SKILL.md` *Commit messages* opens with that judgment: what the change does for whoever meets it after the merge, a user or a party working on a later change. A table gives each kind what whoever meets the change meets, with examples. `feat:` is something new to use or to meet, such as a command, a record format, a refusal on a rule the change itself states, or a thing removed that its users must now work around. `fix:` is behaviour that was wrong against a rule the tree stated before the change, now matching it. `perf:` is the same behaviour, sooner or at less cost. `refactor:` is the same kinds of outcome reached another way, such as a judgment moved from a script to an agent, a gate retired because what it caught did not outweigh its cost, or a skill nobody used, removed. `test:` is a change met nowhere outside the repository's own tests, even a case that refuses where the suite gates the merge. `docs:` is text nobody acts on. `chore:` is upkeep that changes nothing anyone meets, such as the version move, the changelog fold, or a work item's records committed alone. Six clarifications follow, one sentence each. Where a change does more than one of these, its prefix is the one highest in the table. A change's own tests and its work item's records never decide its prefix, so a speed-up with the case that pins it is `perf:`, and a README edit with the case that pins its words is `docs:`. Text a party reads and acts on, such as a skill, an agent definition, a template a party fills or a hook's message, is behaviour, so a change to it is never `docs:` and never `chore:`. "Before the change" is the branch the change merges into, so a commit that builds a rule stated only in its own work item takes the kind its pull request takes. An effect is counted once, by the change that decided it, so a settle that writes a rule change a released work item stated is `chore:`, and a section it rewrites that no released work item decided is that rewrite's kind. The writer states the grounds: the orchestrator's part of the pull request body says in one sentence why the title takes its prefix and names the kind that came closest, and the sealer reads that part against the design and the diff. The branch-name examples follow the table. An issue takes the prefix the pull request that closes it will take, so no issue is filed `chore:` by default. The prefix states what the change is and is never chosen to fit a release number. A repository's own log still decides how a prefix is spelt, and still adds a prefix the table lacks, but no longer decides which row a change takes, because a log written by default teaches the default.
