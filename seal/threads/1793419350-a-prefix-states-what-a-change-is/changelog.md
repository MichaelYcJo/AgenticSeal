### Added

- **The release pull request refuses a release named as a patch whose own commits carry a `feat:` (#1199).** A `feat:` makes a minor. The step that judges the release's milestone, now named `the milestone this release claims is the work it carries, and a patch carries no feat`, also reads the release branch's commit subjects since it left `main` against the version in the branch's name. Where the version's third number is not 0 and a subject opens with `feat:`, the step fails, names each such subject, and states the repair: rename the release's milestone and every later planned `release:` milestone one step forward, cut the branch again under the new name, and move `plugin.json` in the new branch's first pull request. The reading counts the one spelling `feat:`. A subject whose first word is `feat` spelt otherwise, such as `Feat:` or `feat(agents):`, is printed as not read and fails nothing. Every run prints how many `feat:` subjects it counted and whether the version is a patch or a minor, and a minor with none says it ships as the minor it was named. The reading runs where the release's milestone does not exist as well. Of the 37 patch releases from v0.8.1 to v0.25.1, 14 carried a `feat:` subject, under a rule approved on 2026-09-02 that nothing held (#653).

### Changed

- **The prefix table says which change takes which prefix, and a repository's log no longer decides it (#1199).** `skills/commit-pr-convention/SKILL.md` *Commit messages* gives each part of a change one kind, read from what a user, or a party working on a later change, meets differently after the merge, and the change takes the highest kind among its parts as its prefix. The kinds exclude one another, and their order, `feat:`, `fix:`, `perf:`, `refactor:`, `test:`, `docs:`, `chore:`, is the precedence. `feat:` is something to use or to meet that nothing gave before: a command, a record format or a field in one, a step, a reading, or a refusal on a rule the change states. `fix:` is behaviour made to match a rule the tree already stated. `perf:` is the same behaviour, sooner or at less cost. `refactor:` is the same kinds of outcome reached another way, such as a judgment moved from a script to an agent. `test:` is a case added, removed or corrected, which nobody outside the suite meets. `docs:` is text nobody acts on. `chore:` is a part nothing is met through: release preparation, configuration and dependencies that change nothing met, a work item's own records, and a part whose effect a released change already decided. So a speed-up that carries the case pinning it and its work item's records is `perf:`, and a change's tests and records never decide its prefix where it holds a part someone meets. Text a party reads and acts on, such as a skill, an agent definition, a template a party fills or a hook's message, is behaviour, and so are a check outside the tests, a gate, a record's shape and a process step: a part that changes one is `feat:`, `fix:`, `perf:` or `refactor:`, never `docs:`. An effect is counted once, by the change that decided it, so a settle that writes a released work item's rule changes into the policy documents is `chore:`, and a section it rewrites that no released work item decided takes its own kind. The branch-name examples follow the table. An issue takes the prefix the pull request that closes it will take, so no issue is filed `chore:` by default. The prefix states what the change is and is never chosen to fit a release number. A repository's own log still decides how a prefix is spelt, and still adds a prefix the table lacks, but no longer decides which row a change takes, because a log written by default teaches the default.
