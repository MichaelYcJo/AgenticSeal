### Added

- **The release pull request refuses a release named as a patch whose own commits carry a `feat:` (#1199).** A `feat:` makes a minor. The step that judges the release's milestone, now named `the milestone this release claims is the work it carries, and a patch carries no feat`, also reads the release branch's commit subjects since it left `main` against the version in the branch's name. Where the version's third number is not 0 and a subject opens with `feat:`, the step fails, names each such subject, and states the repair: rename the release's milestone and every later planned `release:` milestone one step forward, cut the branch again under the new name, and move `plugin.json` in the new branch's first pull request. The reading counts the one spelling `feat:`. A subject whose first word is `feat` spelt otherwise, such as `Feat:` or `feat(agents):`, is printed as not read and fails nothing. Every run prints how many `feat:` subjects it counted and whether the version is a patch or a minor, and a minor with none says it ships as the minor it was named. The reading runs where the release's milestone does not exist as well. Of the 37 patch releases from v0.8.1 to v0.25.1, 14 carried a `feat:` subject, under a rule approved on 2026-09-02 that nothing held (#653).

### Changed

- **The prefix table says which change takes which prefix, and a repository's log no longer decides it (#1199).** `skills/commit-pr-convention/SKILL.md` *Commit messages* classifies a change by what it gives or asks, and the first row that fits, read from the top, wins. `feat:` is a change after which a user or a party has something to use or to meet that nothing gave before: a command, a record format or a field in one, a step, a reading, or a refusal on a rule the change itself states. `fix:` makes behaviour match a rule the tree already stated. `refactor:` reaches the same kinds of outcome another way, such as a judgment moved from a script to an agent, and nobody gains anything to use or to meet. `docs:` is text no party acts on. `chore:` is release preparation, configuration and dependencies that tell no party to do anything new, and a commit that writes only a work item's own records. Text a party reads and acts on, such as a skill, an agent definition, a template a party fills or a hook's message, is behaviour, so a change to it takes `feat:`, `fix:` or `refactor:` and never `docs:` or `chore:`. An issue takes the prefix the pull request that closes it will take, so no issue is filed `chore:` by default. The prefix states what the change is and is never chosen to fit a release number. A repository's own log still decides how a prefix is spelt, and still adds a prefix the table lacks, but no longer decides which row a change takes, because a log written by default teaches the default.
