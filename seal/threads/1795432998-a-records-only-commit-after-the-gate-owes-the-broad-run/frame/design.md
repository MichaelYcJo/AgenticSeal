## Scope

The mechanisms already hold the rule the issue asks for (G3, G4, G5). This work makes every statement of the rule say it, and pins the arm.

The core's rendered output stays under `lib/core.py#CAP` when the core is rendered from this worktree, whose root is 124 characters long. G23 gives the room that *Scope* items 1 and 2 may add over the base, and item 1 says how the third row stays within it.

In:

1. `skills/core/SKILL.md` *Judgment is not licence to skip a party*, the third row. Its name becomes **No seal without the broad run**. *What it protects* says the sealer guarantees a tree the `Broad gate` command passed at HEAD, or at a commit that only the work item's records follow, and that the sealer reads those records at HEAD itself. *Held by* names its two mechanisms, `agents/sealer.md` step 1 and the same check's broad gate arm, and restates no rule: the rule they read stands in *What it protects*, and for the orchestrator in the paragraph of *Scope* item 3.
2. The same table, the fourth row's *Held by* cell. The guarantee arm fails a ready pull request without `Verdict: sealed` at HEAD or at a commit that only `trail/gate.md` and `guarantee.md` follow. The cell names the two files, since the core defines no term for them and `gaps.md` is called the closing memo.
3. `skills/code-review/orchestration.md` *Orchestrator: the pull request opens once the sealer seals* gains one paragraph, after the paragraph on a conflict with the base, which is the one statement of the rule for the orchestrator. It holds the following facts. A commit after the newest run that changes only files under `seal/threads/<id>/` owes no broad run. Where such a commit changes a record other than `trail/gate.md` and `guarantee.md` after the sealer has written its verdict, it owes `seal pr-body` on the body file and the sealer again, and the sealer reads every record at HEAD. Those two files may follow the verdict's commit, as the guarantee arm reads it (`skills/code-review/scripts/chain_check.py#CLOSING_RECORDS`), so their commits owe neither. A commit that changes any other path owes the broad run again, after the round the core's row *No fix that no round reads* gives it. `agents/sealer.md` step 1 and the pull request check's broad gate arm read the same rule (`skills/code-review/scripts/chain_check.py#follows`). What a `Broad gate` command that reads the records misses is `templates/setup/config.md` *Broad gate*'s (*Scope* item 7), cited and not restated.
4. `skills/code-review/gate-to-pull-request.md`, the paragraph **Commit `guarantee.md`; a verdict other than `sealed` opens no pull request**. The clause "the record commits after the run leave it standing" gives way to a citation of the paragraph of *Scope* item 3. The steps of the repair stay.
5. `skills/implement/orchestration.md`, the table under **Three combinations do not stand**: the first row reads "without the broad run or without the seal". The core section it cites holds where the run must stand.
6. `README.md:286` and its Korean edition `README.ko.md:288`: the broad gate runs at the pull request's head commit, or at one that only the work item's records follow.
7. `templates/setup/config.md` *Broad gate* gains one paragraph, before `### What is refused, and what stays allowed`, for the person who writes the key. A commit after the run that changes only the work item's records does not run the command again (`skills/code-review/orchestration.md` *Orchestrator: the pull request opens once the sealer seals*). A part of the command that reads those records, such as a Markdown lint over every `.md` file or a suite case over `seal/threads/`, therefore reads them as they stood at the run. The pull request's CI reads the later ones where the repository runs the command there, and the repository answers for a command that reads records and runs nowhere else.
8. `tests/skills/test_chain_check.py` *Test_broad_gate* gains one case on the `item` fixture. After a commit of `pr.md` and `changelog.md` under the work item, `chain.broad_gate` returns `[]` and `chain.guarantee` refuses at the same HEAD. After a further commit of `f.txt`, `chain.broad_gate` refuses with `chain.follows_reason(("after", <that commit>, "f.txt"), "the newest gate run")`. The case builds its expected text from the module's own function and copies no refusal string.
9. The one change in `docs/`, in `## Rule changes` below, for the settle.

- **The guarantee arm's set.** A record other than `trail/gate.md` and `guarantee.md`, changed after the guarantee, still owes the sealer again (*Alternatives considered* in `frame/plan.md`).
- **A merge from the base after the gate**, which conflicted only in the records. #1583 asks for that exemption, and it stays in the backlog. The paragraph on a conflict with the base in `skills/code-review/orchestration.md` keeps its rule.
- **The verdict reason `no broad run at HEAD`.** It names the case the sealer withholds in (G14), and three places spell it, a case among them.
