### Changed

- **`seal cost --work-item` names each segment whose spawn prompt also names another work item, and which items (#1510).** A framer's prompt names the release's other work items, so a framer's segment is counted for every item of the release. Each item's page now prints, under its counts, how many of its segments also name another work item and how many other items were read. Below that it prints one line per such segment, with its file name, the other items' directories, and `already in the log` where a comment on the open log already names the segment. The read without `--post` and the posted comment both carry these lines, inside the comment's fence. A later read without `--post` whose segments are all in the log still prints them; a `--post` run with nothing left to post prints only that nothing was posted. The command still counts every segment it counted before, decides no owner, and keeps every exit code. Which run a shared segment belongs to is the orchestrator's judgment, written in its `--says` sentence.
- **The other work items are read from the work item's sibling directories and from every local branch (#1510).** Side by side, each item's directory stands on its own branch until it merges, so the command also lists the records directory at the tip of each local branch and reads each item's `routing.md` there. The four `git` commands it runs only read and fetch nothing, so in a partial clone an item whose `routing.md` the clone does not hold is not read. They run with `GIT_NO_LAZY_FETCH=1`; a git too old to know that variable fetches such a file from the clone's remote. A local-mode records root, under the git directory, is read from its sibling directories alone. Where git is missing or a read fails, the siblings are still read and the exit code does not change. The `seal cost --post` row of *What runs on your machine* in `README.md` and `README.ko.md` says the comment now also names those directories, read from every local branch, pushed or not.
- **`skills/verify/orchestration.md` *Measure the run, and feed the flow log* says a segment whose prompt names several work items is counted for each and named with them, and that the orchestrator judges which run it belongs to (#1510).** The module's usage line, its comment on the work item reading and the `--work-item` help say the same.

`docs/running/measuring-a-run.md` *Where a reading goes* states the old reading until the settle after this release writes the rule change of this work item's `frame/design.md`.
