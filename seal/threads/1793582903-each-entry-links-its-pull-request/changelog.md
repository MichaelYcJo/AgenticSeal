### Changed

- **Each entry of a release note opens with a link to the pull request that added it, and the hidden comment naming its work item is gone (#1139).** An entry used to sit under an HTML comment, `<!-- specs/<work-item-id> -->`, that a reader could not see. Once the settle had removed the work item's directory, the only way back from an entry to the reasons behind it was to search the history for that id. Now the release workflow reads, for each fragment, the oldest commit of the release's range that added it. Where that commit's subject ends with `(#N)`, the number GitHub appends when it squashes a pull request, the entry's first line is `[#N](https://github.com/<owner>/<name>/pull/N)`, and the pull request's body holds the records' text that `seal pr-body` copied there. Where the subject ends with no `(#N)`, the entry is the fragment's text alone, with no link and no commit hash in its place. The same reader serves the release note and `seal settle`, so the two cannot name different pull requests. It reads the oldest adding commit whatever the person's `log.follow` and `log.showRoot` say. The rule is in force from this merge through the work item's rule changes. The settle after the release writes it into `docs/branch-and-release.md` *Cutting a release* and *Work accumulates on a release branch*.
- **`seal settle --apply` keeps a released work item's directory whose version's published GitHub Release note does not carry its entry, and names it (#1139).** The published note is the one copy of a fragment outside the history, and removing the directory leaves the history as the only copy. So where the `seal/` root is committed, `--apply` now checks the note first, for each directory whose record holds no open row. The version is the lowest `vX.Y.Z` tag, by number, that holds the commit adding the work item's `changelog.md`. The note carries the entry where it links the pull request that commit names, under any owner and name, or holds the hidden comment that notes published before this change carry. A directory whose note does not carry its entry is kept, and its line names the tag, the pull request and a `git show <commit>:<path>` for the fragment's text, so the owner can repair the note and run `--apply` again. A version tag with no published release keeps its directory too, unless the repository has published no release at all. The workflow that builds a note from the fragments is AgenticSeal's own and ships with no plugin, so `--apply` reads notes only where some published release opens an entry with a `[#N](https://github.com/<owner>/<name>/pull/N)` line or the old comment. In a repository whose notes are written by hand or by another tool, no note is read and every directory goes as before. A directory with no `changelog.md` or an empty one, which gets no entry, an adding commit that names no pull request, or no version tag has no note to read: it goes as before, and a `no note read:` line under its `removed` line says which case held. The release list is one `gh api --paginate` call, made only where some directory gets as far as a version tag, and the dry run never makes it. A list `gh` cannot give, or a `git` that cannot read the adding commit, stops the run with exit 2 before anything is removed. The closing line counts the directories kept for a note apart from those kept for a row, and exit 1 covers both. Local mode reads no note and removes as before. The rule is in force from this merge through the work item's rule changes. The settle after the release writes it into `docs/the-record-layout.md` *The fold, and what tells it from a deletion* and `docs/release-checklist.md` *2b. Settle what earlier releases left behind*.
