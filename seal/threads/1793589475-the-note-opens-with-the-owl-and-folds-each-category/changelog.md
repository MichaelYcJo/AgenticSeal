### Changed

- **A release note lists each category's pull requests in a fold under the category's name and count (#1153).** The note used to put a heading over each conventional-commit type and every pull request line under it, so a release with many pull requests read as one long list. Now each type that has pull requests is a `<details>` fold. Its summary is the type's name, as the note has always spelt it, and the number of pull requests in it in parentheses, and the fold holds the same lines as before. The types keep their order, and the thanks section, the update section and the full-changelog fold keep their shapes. A title that quotes a `</details>` tag in a code span stays text inside its fold. A title holding a bare `</details>` tag would close its fold early. That is a stated limit, since none of the 318 pull request titles merged by 2026-11-02 held such a tag.
- **A release note opens with a header the seal job completes, the owl beside the stamp's results (#1153).** The note used to open with the release's theme, then an "At a glance" heading over a table of counts, which the seal job replaced with the image on a line of its own and one line of the counts. Now the publish job opens the note with an HTML table of one cell. It holds, one per line, the pull requests merged, the issues they closed, and the outside contributors where there are any. The theme follows it, then the first fold. The seal job replaces that header with a table of two cells. The first holds the seal image, whose alt text is now `The <version> release seal`. The second holds the results the terminal stamp states, as text, one per line: a bold `SEALED` with the version, the tagged commit and its branch, the three counts, the suite's counts, the work items and their review rounds, how many were capped, and the issues deferred. A count that could not be read says so in its line. The seal job edits a note only where the header stands in it exactly once as the publish job wrote it. After its first run the note holds the two-cell header instead, so a second run of the job uploads and edits nothing, and its warning names a run that already replaced the header among the reasons. The rule is in force from this merge through the work item's rule changes. The settle after the release writes it into `docs/branch-and-release.md` *Cutting a release* and `docs/release-checklist.md` *6. After the merge*.
