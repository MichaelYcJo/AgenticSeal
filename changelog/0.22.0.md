### Added

- **Every pull request fails where a rule's `Enforced by:` target is gone.**
  `bin/rules --check` reads every rule file — `CLAUDE.md`, `CONTRIBUTING.md`,
  `agents/*.md`, `docs/*.md`, each skill's `SKILL.md` and `orchestration.md`,
  and `templates/*.md` — and resolves every `Enforced by:` target a renderer
  shows in them. A target that is gone, renamed, defined twice or a constant
  is exit 1, named by file, line and heading. One case of the suite runs it
  over the tree, so the fact is read wherever the suite runs: locally, in
  the sealer's broad gate, and on CI's three legs. It cannot tell a test that
  exists from one that asserts the rule, and a rule with no `Enforced by:`
  line is read by nobody.
  (`1791876665-each-budget-ratchets-and-every-pull-request-measures-it`,
  #930, #923)

- **A release pull request prints one table against the last release tag,
  and the table fails nothing.** The tests workflow's `release-report` job
  runs after the suite on a pull request into `main` only. It sets each
  agent's preload bytes, the suite's seconds, each CI leg's minutes and the
  bytes of `CLAUDE.md`, `CONTRIBUTING.md` and each `docs/*.md` beside the
  same reading at the tag, in the job's summary. A leg's minutes compare one
  run with one run, which swing on the same code, and the table says so.
  (`1791876665-each-budget-ratchets-and-every-pull-request-measures-it`,
  #930, #923)

### Changed

- **Every `bin/` command but `bin/test` refuses a Python older than 3.12 the
  same way, before it reads anything (#929).** Five commands — `settle`,
  `fold-check`, `broad-gate`, `payload-meter` and `seal-stamp` — each
  carried its own copy of that refusal, and eight others ran on whatever
  `python3` they found. All thirteen wrappers and their `.cmd` twins
  now run their script through one launcher, `hooks/launch.py`, which holds
  the floor once. Below 3.12 it prints the sentence the five printed: the
  floor, the version and interpreter it found, *Nothing was read and nothing
  was written*, and the hint that macOS ships python 3.9 as `python3`. Then
  it exits 2 before the script is read. At or above the floor the script
  runs exactly as if it had been run directly. `bin/test` still starts on
  any `python3`, because its runner is what builds a virtualenv at the floor
  from an older one. The plugin's hooks do not go through the launcher, so a
  hook on an older `python3` behaves as before.
  (`1791876666-the-test-suite-is-held-to-a-budget`, #929)
- **The Stop hook draws the sealer's stamp on a `python3` older than 3.12
  too (#929).** The hook loads `seal_stamp.py` in its own process, and that
  file's copy of the floor check made it draw nothing there. The copy is
  gone with the others, so a 3.9 `python3` draws the same stamp 3.12 draws.
  Where `python3` cannot load the file at all, the hook still draws nothing
  and says nothing.
  (`1791876666-the-test-suite-is-held-to-a-budget`, #929)

### Fixed

- **On Windows, `mutation-check` and `arm-check` kept a `--tests` command's
  backslashes (#929).** The command line was split as POSIX shell words, so
  an interpreter's path such as `C:\hostedtoolcache\...\python.exe` lost its
  separators and could not start. A backslash is a path separator there now.
  (`1791876666-the-test-suite-is-held-to-a-budget`, #929)

### Removed

- **The commit-gate test file replays 35 sampled shapes instead of 226
  (#929).** Its S2 case ran every row of the shape corpus against an
  undeclared repository, though the hook sees the commit and not the shape.
  It now runs `SAMPLE`, one or more representatives of each corpus subgroup.
  A sampled row that commits nowhere fails instead of skipping, and a case
  fails when a subgroup has no sampled row. A table of five mutations of the
  gate, the stub installer, the lease reader and the stub's shell shows each
  still caught after the cut. The file holds 178 cases where it held 367, and
  its price in `.test_durations` fell from 1,334 to 441 Windows seconds.
  The sealer file's six corpus layouts that differed from a kept twin only
  by a junit option leave with their 12 ids, and so do the floor-guard cases
  the launcher replaced. 227 ids leave `.test_durations`. The interpreter
  census over every shipped file gives way to one over the code that runs
  before any floor is checked: the hooks, the git hooks, the launcher,
  `bin/test`'s runner and every module they load, which `ruff.toml` now
  lints at Python 3.9, so the linter no longer asks that code for a
  `zip(strict=)` or a `datetime.UTC` its `python3` may lack.
  (`1791876666-the-test-suite-is-held-to-a-budget`, #929)

### Changed

- **Every `tests` run measures `.test_durations`, and the case that says
  when to refresh it is the whole schedule (#931).** 0.21.1 skipped the
  release checklist's refresh box on its first use, because the box asked
  for a 35-minute measuring run a person had to dispatch.
  - Each Windows shard now runs with `--store-durations --clean-durations`
    and uploads the part it measured, and a new `durations` job unions the
    four parts into the `test-durations` artifact. Parts and union are kept
    seven days, and a re-run of failed jobs replaces them, so a partial
    re-run days later still has every part to union. Its summary gives each
    shard's measured seconds, their spread, and the union against the
    committed file. A part that is missing, an id in two parts, or a part
    that does not parse fails the job, and no smaller file is uploaded. The
    job took 7 s and 11 s.
  - `test_the_durations_file_prices_the_suite` now fails in two directions:
    when more than one collected case in twenty has no price, as before, or
    when more than one second in twenty of the file's belongs to cases the
    suite no longer collects. A pull request that removes a twentieth of the
    suite's time therefore brings the fresh file with it. Its message gives
    the refresh: `gh run download <run id> -n test-durations -D <dir>`, move
    the file over the committed one, and commit it. The download needs a
    directory of its own, because `gh` will not write over an existing file.
    A branch with no pull request, or whose run is too old to re-run, gets a
    run with `gh workflow run test.yml --ref <branch>`.
  - The checklist's refresh box, the measuring run and its recipe are gone
    from `docs/release-checklist.md` and `CONTRIBUTING.md`.
  - The first union, from run 38475370013, held 13,930 entries: every case
    collected at that commit priced, none left over, where the file then
    committed left 476 unpriced (3.4 %). Divided by the union, the slowest
    Windows shard ran 1.12 times the mean by pytest's own clock, inside the
    1.10 to 1.20 the unsharded file gave over six runs. The committed file
    is still the one #944 measured; the next refresh the case asks for
    commits a union.
  - The shards priced cases 1.07 times what the single job that measured
    the file before them did, a runner's price level rather than growth in
    the suite; the shards' part ratios move with the runner a group lands
    on, so no scaling is applied to the union. One union moves a single test
    file 0.67 to 1.72 times the level from the next, on files nobody
    changed.

### Changed

- **A review round is one file the warden writes, in words, and nothing
  generates it (#923).** `seal/specs/<id>/rounds/round-N.md`, from
  `templates/sdd-round.md`, opens with a `target:` line naming the commit
  the round reviewed. Under `## Findings` each finding is a
  `### <n>. <symptom>` section with lowercase labels at the start of their
  lines: `severity:` (`must` or `should`, which no check reads),
  `location:` (backticked coordinates where the defect shows), `verdict:`
  (`open`, `fixed <commit>`, `rejected` or `deferred <home>`), a
  `regression:` line where a fix pass's own commits made the finding's
  defect, or a `reopens:` line where it raises again an earlier finding
  whose close does not hold, a `fixed` commit that left the defect standing
  among them, and the fix pass's `answer:`. The
  paste-ready fix sits inside its finding. What the round confirmed is a `confirms:` line under
  `## Confirmations`, left out when there is nothing to confirm; what it
  could not judge is a row of `## Not judged`; the commands it ran are
  `## Probes`. No emoji stands anywhere in a record. The fix pass rewrites
  `verdict:`, writes `answer:`, and adds the coordinate it fixed to
  `location:` where that is somewhere else. No `round-N-report.md` stands
  beside the record any more, and the fields a generator wrote leave:
  `Pass`, `Fixes checked by`, `Needs a fix`, `Written late`, `Fix range`,
  `Contract changes`, `New units`, `Fix of a fix`,
  `Loses a record or crashes`, `Ran by` and `PR`. The rules around the
  rounds are stated once, in `docs/the-review-record.md`: a run ends with a
  verifying round, it has three finding rounds by default, counted from
  the last design change (a reframe, or a new phase the owner approved),
  and extends one at a time while the findings shrink, a finding with a
  `regression:` line is routed by one sentence of its grounds comparing
  the fix with the frame, to the framer where the fix built what the frame
  says and to an ordinary fix pass where it departed from it or was written
  wrong, a fix pass for a regression is followed by one verifying round
  that is not an extension, a
  finding with a `reopens:` line and a defect in a unit a build phase made
  are ordinary findings that get their fix pass, and a leftover finding
  takes the first rung of the filing ladder that fits.
  **A work item in flight when you update** keeps records in the old shape,
  and the check refuses each one by name once its pull request is ready.
  Before you mark it ready, rewrite each of its `rounds/round-N.md` files:

  - The `| Field | Value |` table becomes one line,
    `target: <commit> against <base>`, where `<commit>` is its
    `Target SHA` value, the later commit where it names two. The table's
    other rows and the `Pass` checkbox go.
  - Each 🔴 or 🟡 row becomes a `### <n>. <symptom>` section under
    `## Findings`, `<n>` being the number in its `#` cell. The section
    holds `severity: must` for 🔴 and `should` for 🟡; `location:` holding
    its Location cell's coordinates, each backticked and joined by `, `
    (a `path#unit` becomes its `path`); `verdict:` holding its Verdict
    cell, where `answered`, `withdrawn` and `not a defect` become
    `rejected` if the finding did not hold, `fixed <commit>` if a commit
    repaired it and `deferred <where it was repaired>` if it was repaired
    outside the tree with no commit, `agreed, fixed` becomes
    `fixed <commit>`, and a bare `fixed` takes the commit its grounds name;
    a `regression: round-<K>` line where the record's `Fix of a fix` row
    names the finding, `<K>` being the round whose fixes made the unit, or
    `regression: round-<K>#<n>` where you know the finding whose fix made
    it; its block from `## Paste-ready fixes`; and `answer:` holding what
    the fix pass wrote.
  - Each 🟢 row becomes `confirms: round-<N>#<n>` naming the finding it
    confirmed, or `confirms: none`, with its text on the next line. A
    `carried` row and a `fix-surface` or `fragment` row become `confirms:`
    lines the same way. A ⬜ note row has no place in the new record: keep
    its text as prose under the `target:` line, or open an issue for it.
  - Each ❓ row becomes a row of `## Not judged`, and
    `## Executed probes` becomes `## Probes`. `## What this round was
    asked`, `## Inherited coordinates` and `## Deferred` may stay as prose.

  Every `fixed` or `rejected` finding needs a `confirms:`, `reopens:` or
  `regression:` line in the next record, and the last record may hold
  neither, so a run
  whose last round closed a finding takes one more verifying round. Then,
  in the work item's worktree, run the check from the plugin this update
  installed, with its version and the marketplace you installed it from:

  ```
  python3 ~/.claude/plugins/cache/<marketplace>/specseal/<version>/skills/code-review/scripts/chain_check.py --baseline origin/<base> --worktree
  ```

  and fix what it still names. The other way is to finish that work item
  on 0.21.1 before you update.
  (`1791933022-every-agent-skill-and-doc-states-the-current-rule-only`,
  #923)
- **The check at the pull request reads what a record states in its
  labelled lines, refuses what it cannot read, and a ready pull request
  fails on any refusal (#923).** `chain_check.py` judges the `routing.md`
  naming the pull request's branch and every one its own commits add or
  change. The declaration has to parse. A declared framer left `spec.md`,
  `plan.md` and its mark. A declared review chain left at least one round,
  and four facts hold of its records. Every finding has an answer: none
  reads `open`. Every `fixed <commit>` is a commit on the branch that
  changed a path its `location:` line names. Every `fixed` or `rejected`
  finding of round N is named by a `confirms:`, `reopens:` or `regression:`
  line of round N+1, or it is refused at its own heading. The last round's
  `target:` commit is HEAD or only the work item's own records follow it,
  and none of that round's findings is `fixed` or `rejected`, since no
  round read them. A label in any other spelling (`Verdict:`, `Target SHA`,
  `refixes:`), a value outside its shape (a `path#unit` coordinate among
  them), a missing or doubled line, a finding holding both a `regression:`
  and a `reopens:` line, a finding heading with no number or with a number
  another heading carries, and a fence that never closes are each refused
  by line, never passed.
  `broad-gate.md` names HEAD. `guarantee.md` names HEAD and reads `sound`.
  A draft prints every refusal and fails nothing. A declaration that
  reached the branch inside another pull request's squash, a commit GitHub
  made with a subject ending `(#N)`, was judged at that pull request and is
  named rather than judged again, so a release pull request into `main`
  passes over the items squashed into its release branch. What to do: move
  the `v<version>` in your copy of `templates/hygiene.yml` to this release's
  tag, and delete its step that fetched `refs/pull/*/head`, which nothing
  reads now. From then on, a work item's pull request is marked ready only
  after its sealer has run.
  (`1791933022-every-agent-skill-and-doc-states-the-current-rule-only`,
  #923)
- **The broad run has one home, `broad-gate.md`, on either routing answer
  (#923).** `broad-gate --record <item>` writes it on a green run, newest
  run first with every earlier run kept behind it, where 0.21.1 wrote the
  last round record's `Broad gate` cell for a reviewed item and the file
  only for one that went straight to the pull request.
  (`1791933022-every-agent-skill-and-doc-states-the-current-rule-only`,
  #923)
- **The sealer is the final, independent guarantor, and it runs on Opus
  (#923).** It used to run one command and judge nothing. It now runs after
  the pull request body and the changelog fragment are written, and its
  reference is the issue and the tree, never another agent's account. It
  runs the broad gate, then re-runs a sample of the smith's `executed` and
  `seen red` claims, chosen where the evidence is thinnest, and confirms
  that nothing this release removed has come back. It reads the spec, the
  build, the warden's last round,
  the changelog fragment and the pull request body as one story and names
  the party the issue and the tree contradict. It does not re-judge the
  design or the code's quality. Its
  verdict is `seal/specs/<id>/guarantee.md`, from
  `templates/sdd-guarantee.md`: the claims it re-ran, the parties it
  compared and one `Verdict:` line, `sound`, `not sound — <what>` or
  `undecidable — <question>`. An undecidable question is yours: answer it on
  a line under the verdict, and the sealer runs again at the new HEAD.
  `agents/sealer.md` pins `model: opus`, so a sealer spawn now costs an
  Opus session where it cost one command.
  (`1791933022-every-agent-skill-and-doc-states-the-current-rule-only`,
  #923)

### Removed

  ledger re-read 1,421 prose claims and found 1,420 of them still true, and
  at most 91 false claims surfaced through drift in all that time. In
  0.21.0, 76 % of a release's ledger file was upkeep rows. The record of

  suite is the check. Gone with the ledger:
  1. the data: `seal/ledger.md`, the 45 `seal/releases/*.md` files and
