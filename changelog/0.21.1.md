## 0.21.1 — 2026-10-13

<!-- specs/1791852610-the-routing-question-shows-the-four-boxes-only-under-per-axis -->
### Changed

- **The routing question no longer shows the four per-axis boxes to a person
  who pressed `automation` or `no work item` (#911).** The two questions used
  to go in one `AskUserQuestion` call, and the harness shows every question
  of a call at once, so the boxes were on screen at the start of nearly every
  run while meaning nothing under either answer.

  1. Question 1 is now asked alone. `automation` and `no work item` end the
     asking there.
  2. Under `per axis` the four boxes follow at once, in a second call, before
     the first edit. That answer now costs two clicks where it cost one.

  **Nothing that reads the answer changes.** The worktree guard and the
  commit gate read the `automation` press the same way from either shape, so
  a machine whose installed `CLAUDE.md` block is older still asks the old
  shape and still runs unattended. Run `/specseal:update` there to get the
  new block.

<!-- specs/1791852612-under-automation-a-creation-in-another-clone-asks-nobody -->
### Changed

- **Under `automation`, a worktree creation in another clone no longer
  reaches the person (#903).** The `automation` answer consents to a
  `git worktree add` only in the clone it was given in. A creation in
  another clone, where the session had created no worktree, among idle
  sessions or where sessions cannot be counted, told the model to put two
  options to the person with `AskUserQuestion`, and asked the person
  directly on every attempt after, in a run whose person had said nobody
  would answer.

  1. Under that answer both rows now refuse the creation to the model on
     every attempt. The refusal says the answer consents to a creation only
     in the clone it was given in and that nobody is at the keyboard to
     choose, names no way on, no question tool and no token, and says that
     re-issuing the command unchanged meets the same refusal.
  2. A person sees nothing new. Without the press both rows give the same
     two options and the same prompt after them, word for word, and in the
     clone the answer was given in a creation is allowed as before.
  3. On Windows, where sessions can never be counted, every Bash creation
     in another clone under the press is this refusal.

### Changed

- **`.test_durations` is measured again, and a case now says when it is
  measured next (#874).** The file had stopped pricing 1,276 of the suite's
  13,480 cases (9.5 %). `pytest-split` gives an unpriced case the file's
  mean, so the shards drifted apart and nothing reported it.
  - Every test id is now one spelling on every machine. 205 ids built from
    a path wrote it with a backslash on Windows, and 8 carried the
    interpreter's absolute path, so a file measured on Windows could not
    price them on ubuntu or macOS. A parametrized path now takes
    `ids=posix_id` from `tests/conftest.py`, and
    `test_no_collected_id_carries_the_interpreters_path` refuses an id that
    holds `sys.executable`.
  - The file was refreshed by `CONTRIBUTING.md`'s recipe, as one Windows job
    with `--store-durations --clean-durations` in run 38342987499, which took
    34 m 15 s. It prices all 13,482 collected cases on every leg, and it
    holds no entry the suite does not collect. `--clean-durations` is now
    part of the recipe, so each refresh replaces the file instead of merging
    into it.
  - After the first refresh, the slowest Windows shard ran 1.05 times the
    mean shard and the slowest macOS shard 1.03 times, by pytest's own
    seconds in run 38335775781. The slowest Windows job took 11 m 27 s.
  - `test_the_durations_file_prices_the_suite` fails when more than one
    collected case in twenty has no price (`STALE_SHARE`). Its message names
    the counts and the recipe. It reads the whole collection on every shard,
    and skips when one module is named on its own.
    `bin/test tests -q -k test_the_durations_file_prices_the_suite` runs it
    alone.
  - The release checklist refreshes the file at each release's preparation,
    then has the macOS shards' `timeout` read again by the rule beside the
    values. When the case goes red mid-cycle, the contributor runs the recipe in
    `CONTRIBUTING.md` §Running the checks, whose measuring leg now has a
    budget of 60 minutes.
  - No leg's `timeout` changed. The comment beside the values now names the
    slowest run of each leg: ubuntu 9 m 43 s, a macOS shard 8 m 29 s, and a
    Windows shard 12 m 42 s.

- **`survivor-check` no longer reads a `.test_durations` file or the reader
  census, at any depth (#874).** Both are data keyed by test id or by unit,
  and a line either one drops was read as a corrected sentence. A durations
  refresh rewrites its file whole, and once `--clean-durations` brought the
  file under the 2 MiB size cap, 753 places were reported on one branch. A
  census line leaves `undeclared_readers.txt` when its unit starts to
  declare, and it is spelled exactly as a ledger row cites that unit, so it
  matched every released row citing the unit at that hash. The rule is the
  file's name, never its size.

<!-- specs/1791852614-survivor-check-reads-a-range-as-its-own-commits -->
### Fixed

- **A fix pass's range that holds a merge of the base no longer reports
  another work item's correction as its own** (#873). `survivor-check`
  compared each file at the range's two ends, so after a merge of the base
  a sentence another work item had corrected on the base read as wording
  this range removed, and its standing copy elsewhere was reported as this
  range's survivor. Now, over `a..b`, the sweep still counts the two ends
  and keeps a removed or a written sentence only where one of the range's
  own commits removed or wrote it in that file. The own commits are the
  ones `git log --ancestry-path --no-merges a..b` lists, the rule
  `docs/the-record-layout.md` §*A range owns the commits that descend from
  its start* states for `round-record close`. Wording the merge brought in
  no longer hides an own survivor either. A range with no merge reports
  exactly what it reported before.

  `A...B`, the spelling CI and the broad gate pass, is read at its two ends
  from the merge base, as before. A change made only inside a merge's
  conflict resolution is in none of the range's own commits, so a two-dot
  range no longer measures it.

  The commits a two-dot range lists and does not own are not read, and the
  report now names them on a `not read` line with the advice to write
  `A...B` for a whole branch. So `origin/<base>..HEAD` on a branch that has
  merged its base still reports what it read, and no longer in silence: it
  says which of the branch's commits it left out.

- **`survivor-check` refuses a two-dot range whose start is not an ancestor
  of its end** (#873). Such a range owns no commit, and the sweep used to
  measure it over two unrelated trees. It now stops at exit 2 before
  examining anything, naming both ends and saying to write `A...B` for a
  range whose start is on the base. A `survivors.md` row spelled that way
  is read exactly as before. A range whose own commits git cannot list,
  including a `git log` past its timeout, is refused the same way, at exit
  2 rather than a traceback.

<!-- specs/1791852615-whether-a-ledger-line-is-live-has-seven-rules -->
### Changed

- Whether a ledger or record line is live is stated once, in
  `docs/the-evidence-ledger.md`, and it has three answers because seven
  readers read three kinds of line (#872). A line that holds a claim, an
  anchor or a rider is read when its reader is in doubt, so a parked or
  malformed row is reported and never dropped. A line that excuses or
  declares something, a fold marker or a config row, is not taken on doubt,
  so nothing is excused by a line nobody wrote live. A line a record's rows
  are counted on is blanked the same way on both sides of a comparison. No
  reader's behaviour changed: each of the seven now says in its own
  docstring which answer it gives and what the wrong one costs, and one test
  holds all seven side by side on ten shapes of line, so a reader whose
  answer moves turns a named cell red. `hooks/config.py` and
  `hooks/routing.py` still read a row below a comment opener nobody closed,
  unless a fence that closes holds it, because each keeps the reading it
  gave before its walk was added, and the statement says so.

<!-- specs/1791852616-the-config-table-has-its-own-grammar-beside-the-gfm-walker -->
### Changed

- **`seal/config.md`'s table is read the way GitHub shows it, or refused
  (#871).** The `| Item | Value |` table had a reader of its own — a stop
  rule that stepped past some lines and stopped silently at others — beside
  the walker the plugin holds to cmark-gfm, GitHub's renderer, for the
  pact's tables. It now has only the walker. A row is a row where GitHub
  shows it as one; a line the walker cannot read as GitHub shows it is
  refused in a sentence naming the line and the edit; the rows above that
  line are read, and every row written below it is that refusal, never an
  absent row. What an installed config sees change, shape by shape:
  - a non-blank line directly above the header — a comment, a line of
    prose, a row of something else — was read, and is now refused: leave a
    blank line above the header. A config `seal mode` wrote, or one copied
    from `templates/config.md`, already has that blank line;
  - a header with no delimiter row under it, or one of another width, was
    read as a table GitHub does not render, and is now refused: write
    `|---|---|` under the header;
  - a bare pipe in a value (`| Broad gate | bin/test -q | tee out |`), which
    GitHub shows cut off at the pipe, used to end the table silently and drop
    every row below it to its default; it is now refused, and `broad-gate`
    names the escape: write it `\|`;
  - a third cell, a stray `|---|---|`, or a line of prose among the rows
    used to end the table silently, or was stepped past where no row had
    been read yet; it is now refused: write it as `| … | … |`, or take it
    out;
  - a row under a comment, a fence or a blank line that ends the table was
    read as one of its rows, which GitHub does not show; it is now refused
    as a row the walk never reaches: move it into the table, or, where it
    heads a table of something else, put a heading between the two tables;
  - a row, the header or the delimiter row after a form feed, U+2028 or
    another character only Python ends a line at, on the line above it,
    was read as a line of its own, which GitHub shows as more of the line
    above — and where it is the header or the delimiter row, GitHub renders
    no table at all; it is now refused: put it on a line of its own. The
    pact's `Signer` table and its records are read by the same walk, so a
    signer row after such a character is refused the same way rather than
    read as a signer GitHub does not show;
  - an item written again below the line the walk stopped at, and above the
    next heading, has no value, as an item written twice anywhere has none,
    so the row read above that line is not taken as the answer; a table
    under the next heading is another table's and doubles nothing;
  - a header indented one to three spaces, and a row indented the same way,
    were not read; they are, as GitHub shows them.
- **Every command reading the table refuses an unread row at exit 2, and no
  hook asks anything (#871).** `broad-gate` runs nothing and quotes the line
  — with *write it `\|`* where the line is its own row holding a bare pipe,
  and saying the rows below go unread only where a row is written below it;
  `seal mode` and `seal mode --check` write and move nothing; `fold-check`,
  `correction-check`, `evidence-check --reverify` and `pact-check` judge
  nothing. So a pact line written below the table, which `--reverify` used
  to leave on a `LEFT` line at exit 1, now stops the run on the freeze row
  at exit 2 with the walker's sentence, the ledger untouched — where the
  table holds no `Ledger frozen from` row above that line. Where it holds
  one, the freeze row is read, and the run reaches the `LEFT` line at exit
  1 as before. A row the walk read above the refused line is a value, and
  is used, unless the same item is written again below that line. The mode
  gate reads a refused `Mode` row as an answer it cannot act on and says
  nothing, as it does for a file that will not read; the prompt budget of a
  refused table is zero.
- **`seal mode` no longer writes a second `Mode` row under a bare pipe
  (#871).** The writer reads the walker's table, so it overwrites the line
  the walker read as the `Mode` row, inserts a new one after the last row the
  walker read, and refuses a table the walker refused — the file is left
  exactly as it was, and the line is named.
- **A vendored `evidence-check` carries the walker's line grammar (#871).**
  A copy with no `hooks/` beside it reads the table on the lines it can judge
  alone, follows a fence or an HTML comment above the header to its close —
  so the closed comment `seal mode` writes above every config's header is
  read — and refuses where it lacks the plugin's block state — a block left
  open above the header, an example table inside a block that closes below
  its header, a block line directly under the last row, a fence or comment
  below the table with a row under it — so it may refuse where the plugin
  reads, and never reads where the plugin refuses. Each such sentence says
  what the copy cannot judge and the edit that clears it, or to run the
  plugin's own `evidence-check`. It refuses an item written again below
  the line the walk stopped at, as the plugin does, and a header or a line
  of the table holding a form feed, U+2028 or another character only
  Python ends a line at. Run `/specseal:evidence-ci` to pick it up; until
  then a repository's CI reads with the stop rule.
