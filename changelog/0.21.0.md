### Added

- **Every reader and record of 0.20.0 is inventoried (#834).** The work
  item's `inventory/` (`seal/specs/1791382684-every-reader-and-record-is-inventoried/inventory/`,
  read at the `v0.21.0` tag once `settle --retire` removes the directory) holds 1,467 reader rows across six parts — each unit,

  `guess`), where input it does not understand ends, and where the

  led to are their own issues in this release.

- **The reader registry says where a `Reads:` line's direction is read
  (#834).** In `docs/the-reader-registry.md`, the direction word names where
  an input the unit does not understand ends, followed to the decision its
  value feeds, so a helper's direction is read at its callers and not on its
  own body. It is the meaning the inventory's `Unknown` column was settled
  on, after a reading of the helper's body alone kept giving the wrong word.

### Added

- **Every unit of shipped Python declares what it reads, in its own docstring
  (#835).** Each top-level `def` and `class` in a tracked `.py` file outside
  `tests/test_*.py` carries one line: `Reads: owned|observed|guess — <what it
  reads>; unknown refused|passed|mixed`, or `Reads: nothing — <why>`.
  `tests/test_a_reader_declares_its_input_class.py` refuses a unit with no
  line, a line outside the grammar, and a `nothing` line on a unit that opens
  a file, runs a process, reads the environment or hands text to a
  standard-library parser. A module whose top-level statements read declares
  in its module docstring. Every unit is asked, whatever it calls: a list of
  reading calls only catches a `nothing` that contradicts it, and never
  decides who must declare. The 1,587 units undeclared at landing are listed
  in `tests/undeclared_readers.txt` with their ledger hash, and a listed unit
  owes nothing until it changes; then it declares and leaves the list.
  `docs/the-reader-registry.md` is the rule's home.
- **A frame names what its work removes, and `evidence-check` reads it
  (#835).** `templates/sdd-spec.md` carries a `## Removes` section: one row
  per reader, rule or pin the work takes out of the tree, its coordinate in
  the ledger's grammar without a hash, or the one line `nothing — <why>`. The
  records arm reads each row of a live frame as a claim of absence: a
  coordinate that still resolves reads `STANDING`, and a cell the ledger
  would refuse — no coordinate, a test's node id, a bare symbol in a file no
  parser bounds, a path that escapes the tree, walks through `..` or ends in
  `/` or `/.`, a path that is there and will not read as a file, a path
  carrying a `--map`
  prefix — reads `REFUSED`, never as a removal that happened. A row is read
  in this tree only, never in a migration's original. Both exit 2. A new `seal/config.md` row, `Removes from | <work-item id>`, makes
  the section required for every frame at or above that id; it is read by
  the same reader as `Ledger frozen from` and refused the same way when the
  value is not an id.

### Changed

- **A phase record no longer carries a removal table (#835).**
  `templates/sdd-phase.md`'s *What this phase removes* recorded, once per
  phase, a fact the frame now records once with a check that reads it. A
  removal a phase makes that its frame did not name is a divergence in
  `overview.md`. Phase records already written keep their tables.

  **What an installer sees on upgrade.** A consuming repository whose live
  `spec.md` already holds a `## Removes` heading has its rows read from this
  release on; one that has no `Removes from` row is asked for no section.
  The `Reads:` rule and its census are this repository's own test, and ask
  nothing of a repository that installs the plugin.

  A `seal/config.md` that is there and will not read, or that writes
  `Removes from` twice, now stops a plain `evidence-check` run at exit 2 —
  and so the CI ledger job and the commit advisor. An unreadable file
  already stopped `--reverify`; a doubled `Removes from` does not, because
  `--reverify` reads only `Ledger frozen from`. The records arm reads the
  row through the freeze row's reader, which refuses such a file rather than
  reading it as absent. A repository that declares no `Removes from` row
  meets the unreadable-file refusal too.

### Added

- **A ledger row may name the test that holds its claim, and such a row never
  drifts (#836).** A row's Code grounds cell can name tests as pytest spells
  them — `tests/test_x.py::test_y`, or `tests/test_x.py::TestA::test_b` for a
  method — in place of `path#anchor@hash`. A hashed row records what the code
  held when somebody read it, so every edit to that code owed a re-read; most
  rows written since 0.18.0 were those re-reads. A test row has no hash.
  Read alone, `evidence-check` holds it where the named `def` or `class` is
  defined in its file once, and is `BROKEN` for a test or file that is gone,
  a constant, or a name defined twice (a method written bare is told its
  spelling); a row mixing a test with a code coordinate is `MALFORMED`, and
  a coordinate whose quoted locator holds `::` stays a coordinate. One line
  says the test rows were read for existence alone. `--reverify` writes
  nothing on a test row. A released row moves onto its test by one
  `Corrected ·` row naming the test, written by the branch whose edit drifted
  it, and a released test row whose test was renamed is re-pointed the same
  way; `--into` names that option once when it writes a `Re-read ·` row, and
  so does the commit advisor's repair line under a frozen ledger. A
  repository that vendors the checker through `evidence-ci` updates its copy
  before writing a test row: an older copy reads one as `MALFORMED`.

- **The broad gate holds a test row only where the run it seals saw the test
  pass (#836).** Its ledger arm hands `evidence-check` the pytest record of
  the suite it just ran (`--suite-record`, `--suite-key`). A cited test is
  held where every line the recorder wrote for it says `passed` — a class
  owns its methods and a function its parametrised cases — and is
  `MALFORMED` otherwise, naming what the run did: not run, skipped, xfailed,
  xpassed, failed or error. Nothing about a test is predicted from its file,
  so a test pytest never collected, or a mark in any spelling, is simply a
  line that is not `passed`; a report pytest calls passed with no xfail
  expected of it is a pass whatever word a plugin counts it under (a passed
  subtest), and a case id holding `::` belongs to its function. A test the
  sealing machine skips — a `skipif` true there — refuses the seal there;
  hash that row, or seal where the test runs. A preflight runs no suite and
  reads test rows for existence alone, and where the row loads no recorder
  the gate says on its own output that test rows were read for existence
  alone.

### Changed

- **`fold-check` reads an `Enforced by:` target with the ledger's resolver
  (#836).** A method is now written `path::Class::method`, as pytest and a
  test row spell it, and a name is found where it is defined rather than
  anywhere in the file. Every target in this repository's `docs/` resolves as
  before.

<!-- specs/1791384154-a-records-finding-closes-once-at-the-runs-end -->
### Changed

- **A ⬜ note no longer costs a fix pass and a reader in every round: it is
  carried open and closed once, at the run's end (#837).** A note is a
  finding that reads badly while the behaviour and the fact stay right. It
  used to take a row in its own round's fix table, and a note closed `fixed`
  commissioned a verifying round for a sentence — on one run five notes were
  a record's only fix words and spent the run's one reopening. Now `close`
  leaves a note open and refuses a fix-table row for one, and `new` and
  `close` say how many notes the run carries. When the run has ended — its
  last record reads `Fixes checked by | no fixes to check` —
  `round-record notes --item <dir> --fixes <table> --at <sha>` closes every
  open note of the run in one pass, from a table that names the round beside
  the id, `| Round | # | Verdict | Commit or grounds |`, with the words
  `corrected`, `answered` and `deferred <home>`. A corrected note is written
  `answered` with `corrected at <sha>` as its grounds; `fixed` is refused.
  `notes` refuses before the run's end, `seal` refuses while a note of the
  run is open, `new` refuses a redesign's first record while the stopped
  run still carries one, and `chain-check` fails a ready pull request over
  an open note and, for a work item begun at or after `1791384163`, over a
  note closed `fixed`. The eleven work items framed with this one
  (1791384152–1791384162), which run under the previous `close`, are before
  the cutoff and print; one framed later for this release moves the cutoff
  past its own id. A record whose only open rows are notes now reads
  `no fixes to check` rather than waiting on a reader nothing commissioned.

<!-- specs/1791384155-a-round-record-cell-has-one-reader -->
### Changed

- **The chain check observes a pull request's state and never assumes one
  (#866).** `round-record new`, `close` and `seal` used to hand the chain
  check a draft payload whenever `gh` was absent, failed or said draft, and
  the broad gate did the same for its chain arm; on a machine without `gh`
  every local run was a draft, which excused the unchecked `Pass`, the empty
  `rounds/` and `nobody` beside `Pass` even where `gh` said the pull request
  was ready. The check now reads the payload where GitHub wrote one, else asks
  `gh pr view --json isDraft` itself; where neither answers, nobody observed
  a pull request, so it reads the state as unknown, does not judge it as a
  ready pull request, and prints every source it tried. A record `new`,
  `close` or `seal` just wrote mid-run is not failed for it, and CI, which
  always has GitHub's payload, decides. The broad gate's chain arm passes
  `--sealing` instead of a draft payload, which excuses only the last
  record's `Broad gate` cell — the one that run is about to write — and says
  so on the state line.

### Fixed

- **A round-record cell is read by one reader, in `chain-check`, and every
  other script reads it through that one (#866).** Five judgments were each
  read two to four ways that disagreed:
  - the broad gate's `rounds` row drew `capped` for a bare `yes` and for
    `yesterday …` and missed `**yes — …**`; it reads `Needs a fix` as the gate
    does, and a cell the gate cannot read prints the count alone;
  - a deferral's home is what stands after `deferred` up to the first ` — `,
    as `close` writes it. The panel names that home, the release seal counts
    an issue only where the home is exactly `#N`, and `close` writes the
    rest of the cell into the grounds rather than into the verdict;
  - the depth refusal reads a finding's `Location` the way a fix of a fix
    does, so a name with no `.py` path beside it places nothing;
  - the floor's two walks, the run cut and the premature-gate test are one
    function each, shared by the check and the generator;
  - a doubled close counts only `close`'s own prefixes at the head of the
    Grounds cell, so a reviewer's sentence quoting an earlier close is not
    one, and a field row or a `Pass` box written twice fails at the pull
    request, as the generator already refused.

<!-- specs/1791384156-config-rows-coordinates-and-headings-have-one-reader -->
### Fixed

- **A `seal/config.md` row written twice, and a config that will not read,
  now get one answer everywhere (#867).** A row written twice used to be
  read first-wins by most readers, last-wins by the ledger checker, and
  written first by `seal mode`, so a person could edit the row they saw
  while another one answered. Now it has no value: `evidence-check
  --reverify`, `correction-check`, `fold-check`, `broad-gate` and `seal
  mode` stop at exit 2 naming the row and how many times it is written, and
  `seal mode` names each line. A `config.md` that is there and cannot be
  read as UTF-8 — a directory of that name, bytes another encoding wrote —
  is refused the same way, naming the path, instead of being read as an
  empty config; an absent file still declares nothing. That matters most
  for `Ledger frozen from`: an unreadable config used to turn the freeze
  off, so `--reverify` re-stamped released rows in place. Hooks say
  nothing about either state: the mode gate stays silent rather than
  asking. `chain-check`'s pact notices read the config the same way: one
  that will not read is a notice naming it, and `chain-check --worktree` no
  longer stops with a `UnicodeDecodeError` on such a file. In a
  `routing.md`, a `Review`, `Destination` or `Branch` row written twice
  makes the file no declaration, so the commit gate asks; a doubled
  optional row reads as unanswered.

- **The ledger coordinate has one grammar (#867).** `correction-check`,
  `settle` and the rider check read the checker's own pattern instead of
  copies. `correction-check` now names a dropped correction of a row
  anchored on a path with no extension (`bin/test`) or on a quoted heading
  holding a code span or `\|`, which it could not see before, and no longer
  takes a malformed example quoted in a row for a coordinate.

- **A markdown heading has one spelling, CommonMark's (#867).** A line
  beginning `#120)` used to end a round record's `## Verdicts` or an
  overview's `## Not verified` section above the rows below it, so those
  rows went uncounted. The ledger checker no longer reads a `## B` quoted
  inside a code fence as a heading, so a section anchor runs to the
  section's real end and an example heading in a fence is no anchor. A
  heading indented up to three spaces is a heading. Some released
  heading-path rows drifted once because their section's end moved; a
  repository that freezes its ledger re-reads them with `--reverify --into`,
  and one that does not with `--reverify`.

<!-- specs/1791384157-the-hooks-read-the-session-waiver-and-creation-one-way -->
### Changed

- **The hooks read the session, a waiver and a creation one way each
  (#868), and the worktree guard names a word the shell builds before git
  runs as a limit (#856).** Four facts every gate depends on were read in
  more than one place, and the readings disagreed. Each now has one reader.

  1. Where a worktree creation lands. The consent writer files a creation
     under the clone the worktree guard judged, by the guard's own
     placement. It used to take the first directory it could compute, so
     `eval x ; cd A || git worktree add …` was filed under `A`, the branch
     bash skips, and `cd <missing> ; git worktree add …` filed nothing.
  2. Which process is the session. The lease writer, the commit gate's
     lease route and the guard's count of other sessions test a process by
     one rule, its basename is `claude`, and read `CLAUDE_PID` first where
     the harness exports it. The lease writer reads it only beside its own
     session's `CLAUDE_CODE_SESSION_ID`, so a session started from another
     session's Bash, which inherits the outer pid, records its own process
     instead. The lease writer used to accept any name
     holding `claude`, so it could record a lease no reader matched. The
     git hook stubs test one session variable, `CLAUDE_CODE_SESSION_ID`;
     they also tested `CLAUDECODE`, which nothing behind them read.
  3. Whether a waiver token was typed. The commit gate, the worktree guard
     and the old spelling handed to the git hooks read `[no-review]`,
     `[no-parity]`, `[worktree-ok]` and `[shared-tree-ok]` through one
     reader, which reads the words before a quote that never closes and
     none inside it.
  4. What a failed git call means. The commit gate's two readings run git
     through one runner, which tells an empty answer from a failure.

  What a person meets:

  - A `[no-review]` inside a quote that never closes, or after an
    apostrophe in its comment (`# don't [no-review]`), waives nothing. The
    commit gate used to read it as a substring. The stop names the waiver
    typed in front, `: '[no-review]'; git commit …`. Over the 32,431
    recorded command and directory pairs, one pair's waiver moves.
  - A token written before an apostrophe in its comment (`# [shared-tree-ok]
    the release's own tree`) is still read, by every gate.
  - In a repository declaring `seal/parity.md`, a commit whose `git diff`
    fails meets the parity question, where it was let through as a change
    confined to `docs/` and `seal/`. That includes `git commit -a` or a
    pathspec on a branch with no commit yet.
  - A brace expansion changes nothing the worktree guard says, as at
    0.20.0. `git rebase {main,feature/x}`, `git rebase --ro{,} feature/x`,
    `git stash {branch,} y` and `git worktree {add,} ../wt f` are listed and
    silent in every tree, though bash makes the first three switch HEAD and
    the fourth add a worktree. A reader for them was built and taken out
    inside this release: every reading of it imitated bash, and five review
    rounds each found the next spelling it missed. The guard's policy names
    the brace as a limit beside the other words the shell builds before git
    runs (a substitution that spells `git`, a here-string handed to a shell,
    a git spelled past the splitter), and #886 decides them together.
  - The git hook stubs' bytes change by one variable name, so the installer
    rewrites every opted-in clone's three stubs at the next session, as it
    does when the plugin moves.

<!-- specs/1791384158-the-broad-gate-reads-its-counts-from-the-recorder -->
### Fixed

- **The broad gate's suite counts come from what its own pytest recorded,
  never from what the row printed (#869).** The seal's `suite` row and the
  failure form's counts were read off pytest's printed summary line, so a
  test that printed a summary of its own could put its number on the seal.
  The gate's pytest recorder now writes, for every test report, the category
  pytest's own summary counts it under, and a line for a module that skipped
  itself beside one that failed to import. The panel and the failure form
  count those lines, in pytest's order and wording, and add up every pytest
  session the row ran. Where no pytest the row ran left a record, the form
  says so and names the three causes, instead of saying no summary was
  printed. Where a record holds a line that is not the recorder's, the form
  says how many lines were passed over and prints no count, and a file that
  would read `new` from such a base reads `new?` instead. Where a test had
  no file of its own, so the record could not place it, no count is printed
  either, rather than one short of pytest's own line (#884).
- **The release seal reads the same record through the gate's own reader
  (#869).** The `seal` job runs the suite at the tag with the recorder
  loaded and no JUnit file, and `release_seal.py` takes its passed and
  skipped counts from that record. A record with no session for the run's
  key, a line that is not the recorder's, a session that stopped part-way,
  a test with no file of its own (#884), or a failure or an error in it
  gives no seal, with the reason on a
  `::warning::` line, as an unreadable JUnit file did. Drawing a seal by
  hand now names `SUITE_RECORDS` and `SUITE_KEY` instead of `SUITE_XML`
  (`docs/release-checklist.md`).
- **A malformed `seal-mark.txt` stops the gate with its own sentence
  (#869).** `broad-gate` and `broad-gate --preflight` ended in a Python
  traceback where the disc's mark chart was not in shape. They now exit 2
  before anything runs, saying which file would not load and why.
- **A base that `pytest.exit()`, `-x` or `--maxfail` stopped part-way is no
  longer read as finished (#852).** These stops can end a session with exit
  0, 1 or 5, the same exits a session gives when it ran every test, so a
  file the base never finished read `new`. The recorder now writes on the
  session's last line what stopped it, read from pytest's own hooks and
  flags: an interrupt, `pytest.exit()` with whatever code it chose, `-x` or
  `--maxfail`, or a plugin's stop such as `--stepwise`. The gate reads such
  a session as stopped part-way, so the file reads `new?` naming it, and
  the two stops `templates/config.md` rule 3 left open are closed. Measured
  on pytest 6.1, 7.0 and 9.1, and on 9.1 with pytest-xdist 3.8.

### Removed

- **The stamp's scale (#853).** Since the disc became one size in 0.20.0,
  the scale changed nothing the stamp drew. `--scale` is gone from
  `seal-stamp` and `broad-gate`, and the drawing is byte for byte the same.
  The values file still carries `"scale": 0.9` through this release's
  cycle, read by nothing, because a `Stop` hook or `seal-stamp` from 0.20.0
  refuses a file without one; the release after this one stops writing it.
  A values file draws whether it carries a `scale` or not.

<!-- specs/1791384159-a-unit-the-extractor-cannot-bound-is-refused -->
### Fixed

- **A multi-line TypeScript signature no longer reads `ok` over a rewritten
  body (#848, #870).** A ledger row citing a function by name, in any file
  that is not Python or markdown, was bounded by a rule that guessed where
  the function ends from its indentation. For a signature whose parameters
  run over several lines, the way Prettier writes them, the guess stopped
  before the body, so a rewrite of the body still read `ok` and
  `--reverify` had nothing to notice. Such a row now reads `BROKEN` and
  says what to write instead: a quoted line of the function, whose region is
  the paragraph it sits in. #848's function has no blank line inside it, so
  one quote of its signature covers the whole function, body included.

### Changed

- **A unit is bounded only where a real parser reads it; everywhere else
  the anchor is a quoted line (#870).** A bare symbol (`path#name`) is read
  by Python's own parser in `.py` and `.pyi` files and by the heading path
  in `.md` files. In every other file — TypeScript, JavaScript, Go, Rust,
  Java, Kotlin, Swift, C, C++, C#, YAML, Ruby, shell, a file with no suffix —
  it reads `BROKEN` with "no bounding rule for `.ts`; anchor a quoted line
  instead:" followed by the anchor to write on the row's own path. A quoted
  line (`path#"a line of the unit"`) covers the run of non-blank lines it
  sits in, so a function with a blank line inside it is cited with one quote
  per paragraph, in the same cell. A bare symbol in a `.py` the running
  Python cannot parse reads `BROKEN` naming that Python's version and the
  error's line, where it used to be read by the guessing rule.
  `--migrate` leaves an old `path:line` row in such a file with the same
  sentence as its reason. The anchor it names keeps a `--map` prefix the row
  wrote. A quoted line that is no longer in its file says to quote the line
  as it reads now. A quoted claim inside a unit is no longer grown through
  the lines indented below it: in a `.py` file it is the statement Python's
  parser gives for the quoted line, and anywhere else it is that line.

  **What an installer sees on upgrade.** The commit hook reads the new rule
  at the next commit after the plugin updates; the CI copy under `tools/`
  changes when `/specseal:evidence-ci` is run again. At either moment:
  every row citing a bare symbol in a file that is not `.py`, `.pyi` or `.md`
  reads `BROKEN` with the remedy on its line, including rows the old rule
  bounded right. The repair is one edit per row — quote a line of the unit
  (`path#"<the line>"@00000000`), then run `evidence-check --reverify`, which
  fills the hash; under `Ledger frozen from` the repair is the `Corrected ·`
  row `--reverify` names. A row citing a `.pyi` stub that is decorated, or
  whose signature runs over several lines, reads `DRIFTED` once, because the
  parser takes the whole definition into the span. A row with a quoted claim
  (`path#unit>"a line"`) reads `DRIFTED` once where its claim grew through
  lines indented below the quoted one: in a `.py` file the claim is now the
  statement the parser gives for that line, and in a file no parser reads it
  is the quoted line alone. For each, read the row again, then
  `--reverify`. Every `.md` row, and every `.py` row without a quoted claim,
  keeps its hash and its verdict.

<!-- specs/1791384160-a-fix-range-is-its-own-commits-across-a-merge -->
### Fixed

- **A merge of the base inside a fix range no longer fills the round record
  with another work item's units** (#860). `round-record close` compared the
  range's two ends, so everything a merge brought in counted as this round's
  fixes: one record's `New units` named 111 units, and 109 of them were
  another work item's. Now a range `a..b` owns exactly the commits `git log
  --ancestry-path --no-merges a..b` lists, and `Contract changes` and `New
  units` keep a unit only where one of those commits added or changed it.
  A path filter would not have been enough, because one file the item
  touched carried 22 new names at the two ends and 2 of them were the
  item's. `docs/the-record-layout.md` §*A range owns the commits that
  descend from its start* states the rule.

  `Fix of a fix` reads the previous record's range the same way, so a
  finding inside a unit no own commit wrote reads `no`. `close` now refuses
  two shapes before writing anything: a `--range` whose start is not an
  ancestor of its end, and a `fixed` row naming a commit the range does not
  own — a merge, or a commit not made on top of the start. The `Fix range`
  row's count is unchanged and is still git's own count of `a..b`.

- **The changelog-fragment notice reads the range's own commits instead of
  HEAD's first parent** (#805). It followed HEAD's first parent, so on a
  branch rebuilt on its base with the old tip merged in, it named another
  work item's commit on the base and missed the item's own late fix. It now
  reads what the range from round 1's `Target SHA` to HEAD owns, by the same
  rule as `close`. A commit is named when no own commit that changed the
  fragment descends from it. On a straight history that is every commit
  after the fragment's last change, as before. On CI's checkout, the pull
  request merged into its base, the range also holds every base commit with
  round 1's target as an ancestor, so CI can name a commit a local run does
  not. The notice still prints and never refuses.

- **A file whose name git quotes is read as that file** (#860).
  `round-record` read three git listings as plain text. With
  `core.quotePath` on, which is git's default, a non-ASCII file name arrives
  in quotes and matched nothing. The record therefore missed that file's new
  units, named a call inside it by a quoted path, and could not place a
  finding in it. All three listings are now read with `-z`. A `:` inside a
  path no longer splits it, and a binary file that holds the call is left
  out of the search.

### Changed

- **Under `automation`, a branch switch over uncommitted changes no longer
  asks the person (#894).** In the 0.21.0 run the worktree guard put a
  yes/no to the owner when a `smith` switched branches with one modified
  file, in a run routed `automation` on every item. That row of the guard
  read no press at all. It now has two readers, as the guard's stop for an
  unrecognised shape already had.

  1. Where the person pressed `automation`, the switch is refused to the
     model. The refusal lists the changes and says the guard stops a switch
     while they are present. It names `git commit` and `git stash` as
     commands that pass the guard when run on their own, and leaves which
     one fits, and what comes after, to the model.
     It says nothing about what any kind of switch does with the changes,
     and it is the same text for every kind. Re-issuing the switch unchanged
     meets the same refusal, so the model is told to act rather than retry.
  2. Without the press nothing changes: the person sees the same prompt,
     word for word.

  **What an orchestrating session does differently.** The press lives in
  the session that received it, on the machine it ran on. A run resumed in
  a new session (a `/clear`, a new start, another machine) puts the routing
  question's first question through `AskUserQuestion` again before the
  first spawn. A typed "automation, as before" is not the press, and
  `routing.md` is not read in its place, because the model writes that file.
  `claude --resume` and compaction keep the session, so neither needs it.

### Changed

- **Under `automation`, a branch switch in a tree holding only idle sessions,
  or where sessions cannot be counted, no longer reaches the person (#896).**
  In the 0.21.0 run the worktree guard met a `git switch` beside a lease
  4.7 hours old, told the model to put two options to the owner with
  `AskUserQuestion`, and asked the owner directly on every attempt after, in
  a run routed `automation`.

  1. Where the person pressed `automation`, both rows now refuse the switch
     to the model on every attempt. Where a creation in the switch's clone
     is consented, by that answer in the clone it was given in or by a
     worktree this session already created in that clone, the refusal names
     the way on that needs nobody: split into a worktree with `git worktree
     add` and work there by path with `git -C`. A switch into another clone
     is refused without one, because a split there would be put to the
     person. It names no question tool and no `[shared-tree-ok]`, and says
     that re-issuing the switch unchanged meets the same refusal.
  2. Without the press nothing changes: the person sees the same two
     options and the same prompt after them, word for word.
  3. On Windows, where sessions can never be counted, every `git switch`
     under the press that does not carry `[shared-tree-ok]` is this refusal,
     so an `automation` run there works in a worktree per branch.

- **A session the guard cannot tie to a process no longer reads as working
  right now (#896).** Its line under a guard prompt used to end with a clause
  saying it was working on the tree at that moment, at any age, under a
  header saying none of the sessions could be shown to be working. The line
  now prints the kind of signal and its age and stops there, for example
  `lease declaration 4.7h ago`, in both languages.
