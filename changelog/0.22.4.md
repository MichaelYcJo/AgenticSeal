## 0.22.4 — 2026-10-27

<!-- specs/1792926874-the-records-carry-no-comment-and-the-readers-drop-it -->
### Changed

- **A record carries no HTML comment, and the readers of a record keep no comment state (#1012).** The 173 records under `seal/specs/` that still held template guidance in comments lost it; each `routing.md` keeps its comments, and its reader keeps the walk, because it runs in the commit gate. `unverified_check.py#readable` blanks fenced lines only and reads a comment as text, and `comment_scan` and `strip_comments` are gone. `chain_check.py#unclosed` refuses a fence that never closes and no longer a comment. A `<!--` later in a line is text, so a bare opener in an `answer:` line no longer hides the findings after it. `evals/scripts/replay_targets.py` reads a record from a release tag with the reader of the commit that judged it.
- **A record line that begins with `<!--` is refused at its line (#1012).** The line is one outside every fence whose text, leading whitespace removed, begins with `<!--`. `chain-check` refuses one in a round record, a `guarantee.md` and a `broad-gate.md`. `unverified-check` refuses one in an `overview.md`, and reports a base revision holding one as not compared. `settle` and `chain-check` refuse one in a spec's `## Rule changes`, which is now read with no comment state. The stamp is not drawn from a `guarantee.md` holding one.
- **After upgrading, a repository deletes the comments from its own records (#1012).** A record under its `seal/specs/` that holds a line beginning `<!--` outside a fence is refused at that line until the comment is removed:
  - `unverified-check` reads every `overview.md` under `seal/specs/` on every pull request, so an old overview in any directory turns every pull request red, not only one that touches it.
  - `chain-check` refuses a round record, `guarantee.md` or `broad-gate.md` of each work item the pull request declares, so an in-flight work item framed under the old templates is refused until its records are stripped.
  - `settle` keeps the directory of a released work item whose `overview.md` holds such a line, at the tree or at the merge base of `origin/main`, and holds a spec whose `## Rule changes` holds one.

  The comments are template guidance that nothing reads, and `routing.md` and `seal/config.md` are not affected. No command strips them: the refusal names each line, and a repository deletes the comments by hand or asks its own session to. Whether a later release ships such a command is open with the owner, and until it is answered none ships.

<!-- specs/1792935671-the-routing-check-moves-to-the-sessions-tools -->
### Changed

- **The routing check moved out of git and onto the session's edit tools (#1027).** It governs a session, and inside git it also ran for a person's own terminal commits and held a hooks slot that husky, the pre-commit framework or lefthook need.
  - **What stops being installed into a repository's git hooks: everything.** No `pre-commit`, `reference-transaction` or `post-commit` stub is written, and the installer no longer runs at session start or in every Bash call. A person's commit from a terminal runs no SpecSeal code.
  - **What a session meets instead.** In an opted-in repository, the first `Write`, `Edit` or `NotebookEdit` on a branch no `routing.md` names is refused, with a reason naming two ways on: write the declaration, or run `seal no-work-item` on that branch for a change no work item owns. One run lets the session edit on the branch checked out where it ran, or the branch a paused rebase there names, and on no other branch of the clone; on a detached HEAD outside a paused rebase it records nothing and exits 1, and the refusal there names checking out a branch first. A detached checkout of a commit that a declared branch holds, under that branch's own local or remote-tracking name (a longer branch such as `<branch>/more` does not count), edits without a refusal, so a reviewer's clone at the reviewed commit works; a detached HEAD at any other commit is refused. In a repository whose root is shared (`<repo>/seal/`), every session commit ends with the trailer `SpecSeal-Routing: <work-item-id>` or `SpecSeal-Routing: no work item`, and `chain-check` fails a ready pull request whose commit names a work item no declaration names. In local mode a commit carries no trailer, and `chain-check` prints a work item's trailer it meets there without judging it. A commit someone other than its author committed, such as a person's cherry-pick or rebase of a session's commit or GitHub's squash or rebase-merge, is not judged. Under `straight to the PR`, in a repository that declares `seal/parity.md`, the sealer records the comparison with the original as an `original:` line in `guarantee.md`.
  - **What an existing clone's stubs do after the upgrade.** Each stub runs the plugin copy whose absolute path it names, while that copy is on disk, and does nothing once it is gone. The first session of this release that starts in the clone removes every hook file whose second line is the marker `# specseal-git-hook`, says which, and leaves every other hook file byte for byte. A person can also delete them by hand: `.git/hooks/pre-commit`, `.git/hooks/reference-transaction` and `.git/hooks/post-commit`, where each carries the marker. `.git/specseal-reviewed`, `.git/specseal-parity`, `specseal-judged/` and `specseal-commit-choice/` are no longer read, and leaving them costs nothing.
- **The per-command waivers waive nothing (#1027).** `: '[no-review]';`, `[no-parity]` and `git -c specseal.waive=` are read by nothing in this release, so typing them is harmless and changes nothing. A change that belongs to no work item runs `seal no-work-item` before its first edit, and where the root is shared its commits carry `SpecSeal-Routing: no work item`. An instruction file that still names `: '[no-review]';` for `no work item`, such as a `CLAUDE.md` block installed by an earlier release, waives nothing after this release; SpecSeal does not rewrite anybody's `CLAUDE.md`, and `bash install.sh` puts the current block in place.
- **The stamp is queued when a `guarantee.md` reading `sealed` is written, in shared mode as in local mode (#1027).** The `post-commit` queue is gone with the git hooks, and the edit hook is the one writer of the refusal record for a `sealed` over a commit the branch does not hold.
- **Latency (#1027).** The edit hook adds a median 68 ms to each `Write`, `Edit` and `NotebookEdit` in an opted-in repository: 42 ms the check takes and 26 ms for the hook process the harness starts per edit, measured on macOS with Python 3.12. The installer's median 113 ms leaves every Bash call there.
- **Compatibility (#1027).** A repository's `hygiene.yml` that pins an older plugin release runs a `chain-check` without the trailer arm until a person moves the pin. A session on an older plugin writes no trailer, so its commits are not judged by the new arm.
- **Two defaults stand until the owner answers (#1027).** Both questions are open in the work item's `questions.md`, and this release builds the default of each.
  - Q1, who records the comparison with the original under `straight to the PR`: the sealer compares through `legacy-parity` and writes one `original:` line in `guarantee.md`, which `chain-check` reads.
  - Q2, whether the model may run `seal no-work-item` itself: any session may run it, and the record it leaves, for the session on one branch, is an audit trail in the transcript and in each commit's trailer, not an authorization.

### Changed

- **A gate that stops a session guards the work a work item owns
  (#1031).** This repository's `CLAUDE.md`, *The rule a mechanism is kept
  against*, now says that a gate that stops a session, the routing check
  among them, guards the work a work item owns. A change that would be
  routed `no work item`, such as a formatter run, a dependency bump or an
  identifier renamed across files by `sed`, is outside that work, so where
  only such a change passes through a gap in that kind of gate, the gap is
  not a weakness to close. The checks that run on every pull request are
  not that kind of gate, and the rule does not exempt them. Nothing the
  plugin installs into a consuming repository changes.

<!-- specs/1792976216-the-records-and-the-pr-checks-are-two-answers -->
### Changed

- **Where the records live and whether CI checks pull requests are two answers (#952).** Choosing shared mode no longer installs a workflow that judges every teammate's pull request.
  - **First setup asks three options, in this order:** `shared, records only` (the default) creates `<repo>/seal/` and writes nothing under `.github/`; `shared, with pull-request checks` does the same and then runs `seal pr-checks install`; `local` creates the root under the common git directory and touches nothing in the tree.
  - **The checks are a command of their own.** `seal pr-checks` reports whether `.github/workflows/hygiene.yml` is this plugin's and the release it pins. `seal pr-checks install` writes it from `templates/hygiene.yml`, pinned to the installed release, and stages it; it refuses, writing nothing, where `<repo>/seal/` is not in the tree or a file this plugin did not write is at that path. `seal pr-checks remove` takes out the file this plugin wrote and leaves any other file alone. No config row records whether the checks are installed: the file is the record.
  - **`seal mode local` and `seal mode shared` leave `.github/` alone.** They move the root, stage it and write the `Mode` row. After a switch to local where this plugin's workflow is in the tree, the switch says it stays: pinned to the installed release, that its checks examine nothing and `seal pr-checks remove` takes them out; pinned to another release, or where either version cannot be read, it names the pin, says a release before this one fails every pull request with no `seal/` in the tree, and names the two ways out, moving its `--branch` line to the installed release or running `seal pr-checks remove`; after a switch to shared where no workflow is there, it names `seal pr-checks install`. The way back before the commit is `git reset -- :/seal`.
  - **A pull request that declares nothing passes every step of the workflow.** `unverified-check`, handed a `seal/` root's own `specs` path, exits 0 and names the state where no `seal/` directory is at the working tree's top level, and where every work item under `specs/` lacks an `overview.md` and nothing was deleted against the base. Both were exit 2 before. Any other path holding no `overview.md`, and a misspelt path, are still exit 2. `chain-check` reads nothing as declared where the tree the check reads has no top-level `seal` entry, HEAD in CI and the working tree under `--worktree`, so the pull request that moves the root to local mode with the checks kept, deleting every `routing.md` with the root, passes it too; its commit trailers are still judged.
- **Compatibility (#952).** A repository that already has the workflow keeps it byte for byte, pinned to the release that wrote it, and is not asked again. The `unverified-check` fix reaches that repository's CI only when a person moves the pin: edit the `--branch v<old>` line, or run `seal pr-checks remove` and then `seal pr-checks install`, and commit. A switch to local mode leaves such a workflow in place, and pinned to an older release it fails every pull request there until the pin moves or `seal pr-checks remove` takes it out.

<!-- specs/1792993972-settle-writes-each-sections-latest-decision -->
### Changed

- **`settle` shows the released specs by section and removes; the session running the settle writes each section's latest decision (#1033).** The literal apply in merge order refused a spec whose `from` had gone stale and held every directory with an open row, so a settle could stall on every spec behind one refusal.
  - **The dry run is the timeline.** `settle` groups the released specs whose `## Rule changes` name one section, a section holding its sub-sections, and lists each group in merge order: each operation with its spec's coordinate and whether its `from` and its `to` are in the section now. Two specs in one group that no ancestry orders are marked `unordered`. It lists the specs to read whole (a section that does not parse, or none), every open `## Not verified` row of every released record with the paths it names and whether each is in the working tree, and what `--apply` removes. It refuses nothing.
  - **`settle --apply` removes, and writes no document.** It removes every released work item directory whose record holds no open row in the working tree, with a `spec.md` or without, prints each row the removed records closed with what closed it, keeps and names a directory still holding a row, and exits 1 when it kept one. It no longer asks the merge base of `--released-at` and `HEAD`, and a `--released-at` sharing no commit with `HEAD` is no longer refused.
  - **`skills/settle/SKILL.md` is the settling session's procedure.** For each group it writes the section as the latest decision, checked against the code, the code winning where it has moved on; it decides each open row as moot, answered or a measurement re-homed to an issue, the first that fits where a row fits two, closes it, runs each rule's `check:` targets over what it wrote and the repository's broad gate after `--apply`, again after any fix, so the pull request opens on a passing run with no edit after it, takes a written default where the tree does not decide, and asks nobody. The owner reviews its pull request. The `## Rule changes` grammar is unchanged; `from` locates the text and is no precondition.
- **A work item directory a pull request removes whole reads as a settle where it stood at the merge base (#1033).** `unverified-check --baseline` and `chain-check` no longer ask whether its record was closed at the base or whether `docs/` holds its spec's texts, so a settle's pull request and the release pull request after it pass with the base holding the rows open. A memo removed from a directory that stays, and a row dropped from a table, still fail, and that error now says the directory still stands rather than that a renamed directory reads the same way. The `settled:` and `retired:` notices and the refusal of a `## Rule changes` section that does not parse say the new fact.

<!-- specs/1793051803-settle-runs-in-local-mode -->
### Changed

- **`settle` runs in local mode (#955).** It refused a `seal/` root under the common git directory, so a local-mode repository's policy root never changed. It now reads the work items there, and the settling session follows the same procedure as in shared mode.
  - **A local work item is released when its pull request merged and `--released-at` reaches the merge commit.** `settle` reads the `Branch` row of each work item's `routing.md` and asks `gh pr list --head <branch> --state merged --json number,mergeCommit` once per branch. `gh` names the merge commit whatever the merge method was. A work item with no `routing.md` that `hooks/routing.py` reads as naming a branch, no merged pull request from its branch, or no listed merge commit `--released-at` reaches is unreleased and untouched, and the dry run says which.
  - **The dry run names the local root.** It lists each released work item with its pull request's number and merge commit, and each unreleased one with why. Each spec is read from its directory, and the specs are ordered by their merge commits, two that no ancestry orders marked `unordered`.
  - **`settle --apply` removes each released local directory whose record holds no open row, from the git directory.** No commit holds what it removes, and the dry run names `seal export` for whoever wants a copy.
  - **`settle` run from a subdirectory reads the repository's top, in both modes.** In shared mode it refused there, saying the repository had no `seal/specs/` at either place.
  - **A `gh` that cannot be asked stops a local-mode run with exit 2**: one that is not on `PATH`, a query that fails, or an answer that is not a list of pull requests. Shared mode never asks `gh` and is unchanged.
  - **Limits**: a work item whose branch reached `--released-at` without a pull request stays until it is removed by hand. A repository on a host `gh` cannot ask cannot settle in local mode. A branch name reused after an earlier pull request from it merged reads the later work item as released. So does a merged pull request from a fork whose branch has the same name, since `gh pr list --head` matches a branch's name and not its owner; the one-issue flow names each branch after its issue, which makes either match unlikely and does not rule out the second.

<!-- specs/1793057292-agent-lifetime-and-process-archive -->
### Changed

- **An agent lives one phase, and a fix pass resumes the implementer only while its context is small (#945).** One smith was resumed across every phase and every fix pass of a work item, and in the 0.22.0 run one of them read 941,799 tokens of context in a single turn. Each phase is now a fresh `smith` spawn, handed the phase records the earlier phases wrote and a brief in the shape of `docs/the-review-record.md` *The handoff*, and the orchestrator never resumes a smith across a phase boundary.
  - **A fix pass resumes the implementer only while the implementer's largest per-turn context is below 806,241 tokens, and is a fresh `smith` spawn otherwise.** The implementer is the smith that wrote the last commit the round reviewed. The orchestrator reads that context with `session-cost --segments` on the implementer's own transcript. The threshold is the largest context a fresh, never-resumed smith reached in the 0.22.0 run. A fix pass also takes a fresh spawn where the implementer's session no longer exists.
  - **`session-cost --segments` prints each segment's largest per-turn context**, as a `context` column and a `largest_context` key on each `--json` row. A turn's context is its `input_tokens`, `cache_creation_input_tokens` and `cache_read_input_tokens`, each message counted once. Each slice of a resumed agent's file prints its own value, and a slice with no assistant message prints a dash. The column gates nothing, and the run's `context` line is unchanged.
  - **After the pull request opens, and after each push to it, the orchestrator reads `gh pr view <N> --json mergeable` before it waits on CI.** `CONFLICTING` means GitHub made no merge ref and runs no `pull_request` CI, `UNKNOWN` is read again, and `MERGEABLE` is the answer under which CI is waited on.
  - **A conflict with the base is integrated by merging the base into the branch, never by a rebase.** The orchestrator merges once, after the branch whose changes conflict with this one has landed on the base. Where the merge resolved a conflict in a file outside the work item's records, the orchestrator spawns a verifying round on that resolution, because the chain check reads no merge commit. The broad gate and the sealer then run again.
  - **A decision made after the frame is committed is folded, in place, into `spec.md` or `plan.md` before the next smith spawns.** Until it is folded, the orchestrator keeps one line of its own in `plan.md` naming the comments to fold, below the approval line where the plan carries one and below the title where it does not.
  - **Where a work item stands is read from `plan.md`'s Status column, `overview.md` and the phase records.** The orchestrator that hands the work over writes a `handoff.md` only to move the work to another session or another machine, and the orchestrator that takes the work over deletes it once it has read it.
  - **A problem that recurs within a run gets a prevention home at once**: a mechanism that stops it, or a rule written into the file the recurring act is read from. The work item in progress builds that home, and the orchestrator records it in a comment on that work item's issue.
- **Each release records how the way of working changed (#945).** `templates/process.md` is the shape of `seal/process/<X.Y.Z>.md`: a title and one table, `| Date | Change | Why | Source |`, one row per change. Release preparation writes the file once per release from the milestone's issue comments and the history of `CLAUDE.md`, `agents/*.md` and `skills/*/orchestration.md`. The step stands in this work item's `spec.md` `## Rule changes` until a settle applies it to `docs/release-checklist.md`. The framer reads the archive of the highest version once, where the `seal/` root holds one. The release report, `.github/scripts/release_report.py`, prints each `seal/process/*.md` file's bytes as a row beside the other documents', at the last release tag and now, and fails nothing. No archive file is written for 0.22.0 to 0.22.3.

### Removed

- **The orchestrator's re-run of each hand-back (#945).** Its one catch on record, #929's census defect, belongs to a class each module's own test file now closes, since every census runs over its module there. The warden's rounds, the broad gate and the sealer's re-run of a sample of claims read the work after the hand-back.
- **The unverified record's CI step and broad-gate arm (#945).** The step *the unverified record is readable, and rows leave it closed* leaves `.github/workflows/hygiene.yml` and `templates/hygiene.yml`, and the `unverified` arm leaves `broad-gate`. In 142 failed hygiene runs from 2026-09-23 to 2026-10-25 the step failed in none. The `unverified-check` command, its `--baseline` mode and `settle`'s list of open rows stay.
  - **Failure direction**: the gate allows more. A pull request that deletes a `## Not verified` row, or a whole `overview.md`, instead of closing it now passes CI and the broad gate. A deleted row still meets the warden, who reads `overview.md` in the diff, and the sealer. A wrong allow here costs a lost row of a record, and it cannot break another session's tree.
  - **Prompt budget**: zero. The change removes a CI step and a gate arm, and it asks nobody anything.
  - **Platforms**: the branch's `tests` workflow passed every leg on Linux, macOS and Windows. The removed step ran on `ubuntu-latest`.
  - **What it removes**: the CI step in both workflows, the broad-gate arm with its constants (`UNVERIFIED`, `UNVERIFIED_NAME`, `SPECS`) and its `PARTITION` row, and the release-day ordering duty the step put on `docs/release-checklist.md`, through `## Rule changes`. It adds nothing.
  - **Compatibility**: a repository installed from an earlier release keeps the step until `seal pr-checks install` writes the file again, because the workflow is pinned to the release that wrote it.

### Fixed

- **The root migration removes every directory its move emptied (#1016, #1018).** The migration from `specs/<id>/` into `seal/specs/<id>/` left the work item's directory on disk, empty, and `specs/` with it, in two cases: when the item was merged into a `seal/specs/<id>/` that already existed, and when a move an earlier session stopped was finished. The session-start notice then named the moved item as left where it is and "not a SpecSeal work item". The move now lists each directory again when it reaches it and removes it when that listing is empty, the deepest first. A directory holding an ignored file, such as `.DS_Store`, still stays.
  - **Limits**: a repository the migration already finished is not revisited, so an empty `specs/<id>/` an earlier release left there stays until it is removed by hand. A Windows junction placed by hand under a work item's directory is walked into, and the empty directories behind it are removed too. Where the removal of a directory fails, as on Windows when another process holds it open, that directory and every one above it stay, and nothing is removed by mistake.
