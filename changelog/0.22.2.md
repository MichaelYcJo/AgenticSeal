### Changed

- **Rule 3 of the behaviour evaluation now judges the agent, not one run
  (#966).** `evals/scripts/noninferiority.py#verdict` used to compare each
  shape and reach grader on its own, so one grader losing one of its two
  runs failed a rewrite whose passes rose overall. Now the passes of every
  shape and reach grader both sides ran are added up on each side. The new
  side fails rule 3 where its total is below the baseline's. It also fails,
  naming the grader, where it failed a grader on every run that the
  baseline passed at least once. A grader the baseline lacks still has to
  pass every new run. Rules 1, 2, 4 and 5, every `no result` condition,
  `--runs` and the suite are unchanged, and so is the `model` subcommand,
  which still compares per grader.

  A failing rule 3 writes new lines under `Verdict:` in a record. A falling
  total reads `shape and reach graders passed 29/30 runs on the new side,
  fewer than the baseline's 30/30 (rule 3): ` and then each grader whose
  passes fell, as `<case>/<grader> 1/2 against 2/2`. A grader lost on every
  run reads `shape grader <case>/<grader> failed every new run (0/2) where
  the baseline passed it 2/2 (rule 3)`.

  Where the baseline passed every run of every grader, nothing can offset
  a loss, so one run still decides. #957's sealer record is that case.

  #957's six records, read again under the new rule from their committed
  side files, with no new run:

  | #957 record | As recorded | Shape and reach passes | Under the new rule |
  |---|---|---|---|
  | `warden-phase-2.md` | fail, rule 3 on one grader | 66 → 70 of 72 | pass |
  | `warden-phase-2-run-1.md` | fail, rule 3 on five graders | 66 → 66 of 72 | fail, rule 3 on one grader failed every run |
  | `warden-phase-3.md` | pass | 66 → 70 of 72 | pass |
  | `smith-phase-3.md` | pass | 48 → 48 of 48 | pass |
  | `framer-phase-3.md` | fail, rule 5 | 64 → 64 of 64 | fail, rule 5 |
  | `sealer-phase-3.md` | fail, rules 3 and 5 | 30 → 29 of 30 | fail, rules 3 and 5 |

  The re-read records are this work item's `evals/957-<record>.md`, and
  #957's own records stay as they were judged. So `noninferiority.py check`
  on #957's `warden-phase-2.md` now reports "it says `fail` and its numbers
  give `pass`", because `check` recomputes with the rule that runs it. If
  you run `check` by hand over a record written before this release, read

### Fixed

- **A work item in local mode draws its stamp (#976).** The stamp was
  queued only at the commit of a `guarantee.md` reading `sealed`. In local
  mode the `seal/` root sits under the git directory, where no commit
  carries it, so a local-mode work item never drew one. A new `post-edit`
  hook, `sealer-stamp-queue`, now queues the stamp at the `Write` or `Edit`
  that leaves a local root's `guarantee.md` reading `sealed`, and prints the
  line `post-commit` prints in shared mode, naming the queued file and
  `seal-stamp --from`. The `Stop` hook draws it at the end of the turn, as
  before. It is queued once per work item, and only where the audited
  commit is on the branch the work item's `routing.md` names, so editing a
  guarantee sealed long ago draws nothing. Every other file edit is passed
  over on its path alone, before anything is loaded or any `git` runs.
  Shared mode is unchanged. A local guarantee that arrives by a shell write
  or `seal import` queues nothing.

  The sealer's definition lost one word, `committed`, since a local-mode
  verdict is never committed. So it was measured again against #975's
  phase-4 side on the same five-case suite:

  | Agent | Tree | Preload bytes | Tokens per tool call | Spend USD | Graders passed | Verdict |
  |---|---|---|---|---|---|---|
  | sealer | `981b0acc` → `f99ab3a9`, one suite (`5c3e8119`) | 24,700 → 24,690 | 35,992.6 → 35,600.6 | 3.5731 → 3.3379 | 68 → 68 of 68 | pass |

  Each figure is read from `evals/sealer-phase-5.md`, which compares #975's
  `evals/sealer-phase-4.json` with this work item's
  `evals/sealer-phase-5.json`. Both sides are 10 runs, two of each case, and
  neither was cut short.
  (`1792363231-a-local-mode-work-item-draws-no-stamp`, #976)
- **A `sealed` over a commit the work item's branch does not hold is refused
  at its commit, and its repair draws the stamp (#976).** Since #975, a
  `sealed` whose audited commit was not on the branch drew nothing. Yet once
  committed it counted as the work item's one stamp, so the corrected re-seal
  drew nothing either. Now the commit gate inside git refuses, in
  `pre-commit`, a commit that stages such a `guarantee.md` on the branch its
  `routing.md` declares. The refusal names the file, the commit the row
  names, the branch and HEAD, and the one way on: a new audit of the sealer
  at HEAD. It has no waiver. Before it prints, the hook leaves an empty file
  under `<git-common-dir>/specseal-stamp-refused/`. The earlier-run chain
  skips a `sealed` that file names, so the new audit, which keeps the
  refused verdict on its row, draws the stamp. In local mode the edit hook
  writes the same record and says one line naming the commit and the branch.
  A wrong row committed where the gate does not run, under `--no-verify` or
  in a foreign hooks slot, still leaves its work item with no stamp. Three
  more limits are stated, none of which arises in this plugin's own flow:
  a wrong row an amend folds into the commit it audited leaves no stamp; a
  sealed item copied onto its branch in a second clone draws a second stamp
  there; and a conflicted merge that brings in a side's `sealed` is
  refused, with `--no-verify` as its way on.
  `docs/the-review-record.md` §*The stamp* states each. On one machine,
  as medians of 11 commits, an ordinary judged commit takes 268 ms against 260 ms
  before, and one staging a `sealed` guarantee 310 ms against 283 ms.
  (`1792363231-a-local-mode-work-item-draws-no-stamp`, #976)

### Added

- **A side already paid for is graded again under another suite's truths,
  with no run (#971).** `evals/scripts/noninferiority.py regrade --side
  IN.json --suite-rev REV --out OUT.json` grades each run of a committed
  side on REV's `truth-` graders, searching each grader's regex over the
  run's report rows. It writes the side again with the scores following, and
  names the suite its runs answered in `specseal.regraded_from`, kept
  through any number of regrades. It exits 2, naming the
  case, in these cases:
  - the side's own suite does not give back from its rows what it recorded;
  - REV differs from the side's suite in anything but `truth-` graders;
  - REV holds other cases;
  - a truth is one no report row can answer.

  #957's two warden sides, regraded onto af9c924b, give back their recorded
  figures: 55 rows with 43 false, and 47 rows with 31 false.

### Changed

- **The pull request opens once the sealer has sealed, and CI runs then
  (#943).** The orchestration used to open a draft pull request at the end
  of the build, before round 1. CI then ran the suite on three platforms at
  every push of every round, and marking the draft ready ran it once more on
  a commit it had already run. Now the branch is pushed freely while it is
  built and reviewed, and a branch with no pull request runs nothing. The
  pull request opens ready after `guarantee.md` reading `sealed` is
  committed, with the body the sealer read. A run whose routing says
  `stop before the pull request` pushes nothing and hands the branch back
  committed and unpushed, as before. Where the work's risk is
  specific to one platform, the orchestrator runs
  `gh workflow run tests --ref <branch>` once the build's last phase closes
  and reads the result before its broad run. The stated limit: a defect that
  only one platform shows, in work nobody expected to be platform-specific,
  is found when the pull request opens, after the sealer. Its fix takes the
  existing repair path: a verifying round, the broad run again and the
  sealer again, and a repaired body is given to the open pull request with
  `gh api -X PATCH`. A repository whose people still open drafts is not refused,
  because `chain_check` still excuses a draft and `hygiene` re-runs it when
  the draft is marked ready.

  The owner section in `skills/code-review/orchestration.md` is now titled
  *Orchestrator: the pull request opens once the sealer seals, and a phase
  is re-run*, and every document citing it moved with it. The sealer is
  spawned before the pull request exists and reads its body from a file the
  prompt names. `broad-gate --record`'s last line now reads
  `CI reads HEAD, so commit it before you push`. The framer's route no
  longer labels the pull request `chain: reframed`: it runs before any pull
  request exists, and nothing read the label.

  The sealer's definition changed, so it was measured against #976's side
  on the same five-case suite:

  | Agent | Tree | Preload bytes | Tokens per tool call | Spend USD | Graders passed | Verdict |
  |---|---|---|---|---|---|---|
  | sealer | `f99ab3a9` → `95ab5fd0`, one suite (`5c3e8119`) | 24,690 → 24,505 | 35,600.6 → 35,906.3 | 3.3379 → 3.0371 | 68 → 68 of 68 | fail, rule 5 alone |

  The rule-5 fail is 0.9%, with total tokens down 10% and tool calls down
  from 81 to 72; the first side of the same change, 117 bytes longer, read
  35,060.4 per call. It is recorded as it reads and shipped, the owner's
  rule for a rule-5-only fail with every outcome grader holding.
  `evals/sealer-phase-3.md` and `evals/sealer-phase-3b.md` hold both sides.

- **`tests` no longer runs when a draft is marked ready, and a newer push
  cancels the older run (#943).** `.github/workflows/test.yml` dropped
  `ready_for_review` and `converted_to_draft`: nothing in it reads draft
  state, so those events only re-ran the suite on the same commit.
  `hygiene.yml` keeps them, because `chain_check.py` reads draft state. Both
  workflows declare a concurrency group per workflow and pull request, and a
  newer pull-request run cancels the one still in progress. A run that is
  not a pull request's, such as a push to `main`, takes a group of its own
  (`github.run_id`), so it is never held pending or cancelled.
  `tests/test_ci_gives_the_checks_what_they_need.py` requires the draft
  events exactly where a workflow runs `chain_check.py`, and holds the
  concurrency block.
  (`1792367880-ci-runs-once-when-the-pull-request-opens`, #943)

### Changed

- **Every finding in a round record names what its claim rests on, and the
  check refuses one that does not (#985).** A finding carries one
  `evidence:` line. `evidence: executed` is followed by each command the
  round ran, and `evidence: read` by each `path:line` or `path:first-last`
  it opened, each backticked and joined by `, `. `chain_check` refuses a
  finding with no such line, with two, with the label spelt another way, or
  with a value of another shape, at its line and with the reason. The line
  is one row of the grammar table in `docs/the-review-record.md` §*The round
  record*, and the check's code did not change. A backtick ends a command
  on the line, so a command that holds one is written and run with
  `$(printf '\140')` in place of the character.

  A claim of absence, that nothing catches, calls or states something, is
  `executed` only, because no line opened can show an absence. The check
  cannot tell whether a claim is one of absence. The warden that writes the
  line and the round that reads it judge that. A later round re-runs an
  earlier finding's `executed` line rather than deriving the claim again.

  `agents/warden.md` names the line among a finding's lines and states the
  absence rule where it ordered the coverage probe. The warden's preload is
  27,168 bytes, 5 fewer than before. `templates/sdd-round.md` and
  `skills/code-review/SKILL.md` carry the line in place of the old
  "executed and read labelled apart".

  | Agent | Preload bytes | Tokens per tool call | Spend USD | Recall | False rate | Verdict |
  |---|---|---|---|---|---|---|
  | warden | 27,173 → 27,168 | 87,862.4 → 85,306.7 | 41.7424 → 39.7893 | 19 → 13 | 0.558 → 0.641 | fail on rules 1 and 2, recorded as noise and shipped by the owner |
